# سیاست داده روی سرور (Production) — GYM CONTROL

**تاریخ قفل:** ۱۴۰۴-۰۸-۲۲ (2026-11-12)  
**منبع:** تصمیم صریح صاحب پروژه — از این به بعد برای محیط سرور/پروداکشن اجباری است.

## به زبان ساده

روی لپ‌تاپ توسعه گاهی دیتابیس را خالی می‌کنیم و دوباره **دادهٔ ساختگی (فیک)** می‌ریزیم تا سیستم پر دیده شود.  
روی **سرور اصلی** این کار **ممنوع** است: دادهٔ قبلی باشگاه نباید پاک شود؛ آپدیت نرم‌افزار فقط **افزایشی** است (کد جدید + migration)، نه ریست.

---

## قوانین قرمز (اجباری)

1. **هیچ wipe / clear / truncate دامنه روی production** — نه دستی، نه در اسکریپت دیپلوی، نه در CI.
2. **`python -m app.db.wipe_dev_data` روی سرور اصلی هرگز.**  
   در کد هم با `APP_ENV=production|staging|prod` بدون `ALLOW_DESTRUCTIVE_SEED=true` رد می‌شود — و آن فلگ روی سرور واقعی باید **همیشه false** بماند.
3. **`wipe_and_seed` / seed حجیم توسعه** روی DB واقعی اعضا ممنوع. seed لوکال برای دمو است، نه برای پر کردن باشگاه واقعی.
4. **Migration فقط جلو می‌رود:** `alembic upgrade head` — بدون downgrade مخرب روی دادهٔ زنده مگر پلان بکاپ+تأیید صاحب.
5. **دیپلوی = جایگزینی کد + schema سازگار**؛ ردیف‌های قبلی (اعضا، پرداخت، حضور، …) می‌مانند و دادهٔ جدید فقط **اضافه** می‌شود.
6. **هیچ دادهٔ واقعی عضو در گیت یا seed فیک نیست.**

---

## حساب‌های مجاز روی سرور (برای تست دود)

روی سرور، به‌جای هشت عضو فیک و ده‌ها ردیف seed، حداکثر این چهار نقش تست (اگر هنوز نیستند، **فقط در صورت نبودن** ساخته شوند — upsert/insert بدون پاک کردن بقیه):

| نقش | تعداد | چطور |
|-----|--------|------|
| مدیر | ۱ | `python -m app.db.bootstrap_manager` (فقط وقتی هیچ مدیری نیست) یا مسیر امن بعدی |
| منشی | ۱ | از پنل مدیر بعد از ورود، یا اسکریپت idempotent «اطمینان از وجود» |
| مربی | ۱ | همین |
| عضو (ورزشکار) | ۱ | همین؛ موبایل واقعی برای تست OTP در صورت نیاز |

- اگر این حساب‌ها از قبل روی سرور هستند → **دست نزن / پاک نکن.**
- اگر دادهٔ واقعی باشگاه هم هست → فقط همان را نگه دار؛ seed فیک اضافه نکن.
- رمزهای تست را بعد از اولین ورود واقعی عوض کن؛ رمزهای `ChangeMe123` seed لوکال روی prod نگذار.

---

## لوکال در برابر سرور

| عمل | لوکال / DB تست | Production |
|-----|----------------|------------|
| `wipe_dev_data` | مجاز روی DB توسعه | **ممنوع** |
| `seed` حجیم فیک | OK (افزایشی؛ wipe جداست) | **ممنوع** |
| `alembic upgrade head` | OK | **اجباری قبل/همراه دیپلوی** |
| ساخت ۴ حساب دود | اختیاری | فقط اگر خالی‌اند؛ بدون wipe |
| پاک کردن اعضای واقعی | — | **هرگز از مسیر دیپلوی** |

---

## چک‌لیست قبل از هر دیپلوی به سرور

- [ ] `APP_ENV=production` (یا staging جدا با DB دورریختنی)
- [ ] `ALLOW_DESTRUCTIVE_SEED` ست نشده یا `false`
- [ ] دستور دیپلوی شامل `wipe` / `seed` کامل نیست
- [ ] فقط `alembic upgrade head` + ری‌استارت سرویس + بیلد فرانت
- [ ] بکاپ تازه قبل از migration بزرگ — [backup.md](backup.md)
- [ ] بعد از دیپلوی: health OK؛ لاگین مدیر قبلی هنوز کار می‌کند؛ تعداد اعضا کم نشده
