# توافق همکاری (Vibe Coding)

این سند ترجیحات کار با Cursor روی پروژهٔ GYM CONTROL را ثبت می‌کند تا بعداً معلوم باشد *چرا* این‌طور پیش می‌رویم.

**تاریخ ثبت:** ۱۴۰۴-۰۷-۲۲ (2026-10-14)  
**منبع:** درخواست صریح صاحب پروژه در چت

---

## ۱) همه‌چیز را مستند کن

- هر تصمیم، ترجیح، یا محدودیت مهمی که در چت گفته می‌شود باید در `docs/` ثبت شود.
- هدف: چند هفته بعد بتوانیم بفهمیم «این کار برای چه انجام شد؟»
- محل‌ها:
  - تصمیم معماری → `docs/adr/`
  - راهنمای اجرا / نصب / همکاری → `docs/guides/`
  - مشخصات محصول → `docs/product/`

## ۲) هر کار را توضیح بده

- بعد از هر تغییر معنادار، یا توضیح کامل بده یا خلاصهٔ واضح — بسته به پیچیدگی.
- صاحب پروژه باید بداند *الان چه کاری انجام شد* و *چرا*.

## ۲٫۱) پاسخ فارسی و RTL

- همهٔ پاسخ‌های چت به صاحب پروژه **فارسی** و مناسب خواندن **از راست به چپ** باشند.
- کل جواب را انگلیسی/LTR ننویس؛ اصطلاح فنی انگلیسی را کوتاه داخل جملهٔ فارسی بیاور.
- قانون پروژه: `.cursor/rules/rtl-persian-responses.mdc`
- قانون سراسری Cursor (User Rule): «پاسخ فارسی و RTL در همهٔ چت‌ها»
- برای دیده شدن واقعی RTL در چت Cursor: کل پاسخ داخل `<div dir="rtl">…</div>`

## ۲٫۲) Agent خودش docs و ساختار را پیدا کند (نه صاحب پروژه)

صاحب پروژه نباید هر بار مسیر فایل، لینک GitHub، یا فهرست docs را در پرامپت تکرار کند.

**اجباری برای Agent:**
1. در شروع کار معنادار، خودش `docs/` (از جمله `docs/README.md` و guides/ADR/product) و ساختار ریپو و قوانین `.cursor/rules/` را بخواند/اسکن کند.
2. پرامپت‌هایی که برای چت جدید به صاحب پروژه می‌دهد باید **کوتاه و هدف‌محور** باشند؛ بدون لیست طولانی آدرس docs یا URL گیت‌هاب مگر صاحب پروژه صریحاً بخواهد.
3. دانستن محل مستندات و قراردادهای پروژه جزء دانش کاری Agent است، نه جزء کارِ کاربر.

## ۳) سبک کار: Vibe Coding

پروژه عمدتاً با vibe coding جلو می‌رود (ایده → ساخت توسط Agent → بازخورد).

### مفاهیم تخصصی را ساده توضیح بده

اگر موضوعی تخصصی است (مثلاً FastAPI، migration، CORS، JWT، ORM):

1. اول بگو **این چیز چیست** به زبان ساده
2. بعد بگو **در این پروژه به چه درد می‌خورد**
3. اگر سؤال تخصصی از صاحب پروژه لازم است، همان‌جا مفهوم را کامل توضیح بده؛ سؤال را خشک و مبهم نپرس

### واژه‌های پرتکرار (مرجع سریع)

| اصطلاح | یعنی چه؟ |
|--------|----------|
| **API** | درِ ورودی سرور؛ فرانت از طریق آدرس‌هایی مثل `/api/v1/members` داده می‌گیرد یا می‌فرستد |
| **FastAPI** | فریمورک پایتون برای ساخت همان APIها |
| **Endpoint** | یک آدرس مشخص API (مثلاً «سلامت سیستم» یا «لیست اعضا») |
| **Frontend** | چیزی که کاربر در مرورگر می‌بیند (اینجا React) |
| **Backend** | منطق و داده روی سرور (اینجا Python + FastAPI + Postgres) |
| **Database / PostgreSQL** | محل ذخیرهٔ دائمی اعضا، پرداخت‌ها، حضور و … |
| **ORM (SQLAlchemy)** | به‌جای نوشتن SQL خام زیاد، با کلاس‌های پایتون با جدول‌ها حرف می‌زنیم |
| **Migration (Alembic)** | نسخهٔ کنترل‌شدهٔ تغییر ساختار جدول‌های دیتابیس |
| **Environment / `.env`** | تنظیمات محرمانهٔ محلی (رمز دیتابیس و …) که به گیت‌هاب نمی‌رود |
| **ADR** | سند کوتاه «چه تصمیم معماری گرفتیم و چرا» |

## ۴) قبل از کار مهم، اگر لازم است بپرس

- اگر برای ادامه به انتخاب/تأیید صاحب پروژه نیاز است → **اول بپرس، بعد از تأیید اجرا کن**
- اگر کار واضح است و تأیید قبلی وجود دارد (یا فقط مستندسازی/رفع باگ واضح است) → **بپرس نکن؛ شروع کن** و صاحب پروژه را در جریان بگذار

## ۵) همیشه در جریان پروژه نگه دار

در پاسخ‌ها مشخص باشد:

- الان کجای مسیریم
- همین لحظه چه کار شد / می‌شود
- قدم منطقی بعدی چیست

## ۶) تست قبل از GitHub

برای هر قابلیت مهم باید تست خودکار نوشته و اجرا شود.

- فقط اگر تست‌ها **سبز** بودند → commit و push
- در چت بگو قابلیت کاملاً OK بوده یا نه

جزئیات: [testing.md](testing.md) · قانون Cursor: `.cursor/rules/testing-and-ship.mdc`
