# الگوی کامل پروژهٔ اصولی (قابل‌تکرار)

**تاریخ ثبت:** ۱۴۰۴-۰۷-۲۴  
**آخرین گسترش:** ۱۴۰۴-۰۷-۲۶ (2026-10-18) — نسخهٔ دقیق بر اساس مسیر واقعی GYM CONTROL  
**هدف:** برای هر پروژهٔ بعدی همین *نظم* را کپی کنی — نه لزوماً همان پشتهٔ React/FastAPI.

این سند **کتابچهٔ روش کار** است. وضعیت لحظه‌ای باشگاه در `roadmap-status.md` می‌ماند.

---

## نقشهٔ ذهنی یک‌صفحه‌ای

```text
ایده
 → پروتوتایپ قابل‌دیدن (ماکت)
 → docs + قوانین همکاری + ADR
 → اسکلت محصول واقعی + تست سلامت
 → مشخصات رفتار (business rules)
 → مدیرمحصول / سازنده (دو چت)
 → مدل داده + migration + seed
 → auth سمت سرور
 → برش‌های عمودی + تست سبز + به‌روز docs
 → پول/حساس‌ها + audit
 → قبل از دادهٔ واقعی: HTTPS + بکاپ + اسکن امنیت
```

**قانون طلایی:**  
ماکت جدا از مغازه؛ قوانین قبل از حدس؛ داده قبل از پنل شلوغ؛ ورود قبل از دادهٔ حساس؛ هر برش با تست سبز تمام می‌شود.

## فاز ۰ — شروع و توافق کار با AI

### چه کردی در Gym؟
سبک vibe coding را رسمی کردی: مستند کن، ساده توضیح بده، قبل از کار مبهم بپرس، Agent خودش docs را پیدا کند.

### برای پروژهٔ بعدی بساز / بنویس
| چیز | یعنی چه |
|-----|---------|
| قانون همکاری | چطور با Cursor کار می‌کنی (مثل `docs/guides/collaboration.md`) |
| قانون کشف زمینه | کاربر مسیر فایل نچسباند؛ Agent از `docs/README.md` شروع کند |
| زبان پاسخ | اگر مخاطب فارسی است: RTL واقعی (`dir="rtl"`) |
| مرز نقش‌ها | بعداً: چت مدیر محصول ≠ چت سازنده |

### خروجی این فاز
قرارداد «چطور حرف می‌زنیم و کجا می‌نویسیم» — هنوز لزوماً کد محصول نیست.

## فاز ۱ — پروتوتایپ قابل اجرا (ماکت محصول)

### این چیست؟
نسخه‌ای که *شکل و جریان* را نشان می‌دهد، بدون ادعای امنیت/دادهٔ واقعی.

### چه کردی در Gym؟
- چند صفحهٔ HTML + CSS (Ocean Dark): لندینگ، منشی، مدیر، ورزشکار
- روی **GitHub Pages** منتشر شد تا روی موبایل/لینک ببینی
- تم‌های جایگزین محلی ماندند و به گیت نرفتند

### برای پروژهٔ بعدی
1. یک ماکت بساز (HTML ساده، Figma+استاتیک، یا Vite فقط‌UI بدون API واقعی).
2. طوری باشد که **بدون دیتابیس** باز شود.
3. اگر خواستی لینک عمومی: GitHub Pages از **فایل‌های ثابت** (مثل ریشهٔ HTML)، نه از API+Postgres.
4. صریح بنویس: «این پروتوتایپ است، محصول واقعی نیست.»

### اشتباه رایج
ماکت را با لاگین جعلی و «دکمهٔ قایم» جای سامانهٔ واقعی بگیری.

## فاز ۲ — ساختار ریپو و مرز لایه‌ها

### ساختار پیشنهادی (الگوی Gym)

```text
Project/
├── docs/                 # منبع حقیقت نوشتاری
│   ├── product/          # مشخصات و وضعیت محصول
│   ├── adr/              # تصمیم‌های معماری
│   ├── guides/           # چطور کار کنیم / تست / امنیت / شروع
│   └── prompts/          # پرامپت آمادهٔ سازنده
├── frontend/             # محصول واقعی UI
├── backend/              # محصول واقعی API
├── index.html …          # فقط پروتوتایپ / دموی Pages (اختیاری)
├── .cursor/rules/        # قوانین همیشگی Agent
├── .cursor/skills/       # مهارت‌هایی مثل مدیر محصول
├── .gitignore            # .env، venv، node_modules، رمزها
└── README.md             # کوتاه + لینک به docs
```

### مرز اجباری

| لایه | کجاست؟ | اجازه دارد چه باشد؟ |
|------|--------|---------------------|
| پروتوتایپ | HTML ریشه یا پوشهٔ demo | ظاهر و جریان نمایشی |
| محصول واقعی | `frontend/` + `backend/` + DB | فیچر جدید، تست، امنیت |
| اسرار | `.env` محلی | هرگز در گیت |

### خروجی
همه می‌دانند کد جدید کجا نوشته می‌شود.

## فاز ۳ — مستندسازی از روز اول (docs hub)

### انواع سند (جدا نگه دار)

| نوع | پوشه / فایل نمونه | محتوا |
|-----|-------------------|--------|
| فهرست | `docs/README.md` | فهرست همهٔ docs |
| مشخصات پروتوتایپ | `docs/product/*-prototype.md` | صفحات، نقش‌های نمایشی، مدل نمونهٔ UI |
| قوانین کسب‌وکار | `docs/product/business-rules.md` | **منبع حقیقت رفتار** (مقدم بر ماکت) |
| وضعیت زنده | `docs/product/roadmap-status.md` | الان کجاییم / بعد چیست / الان نکن |
| TODO مدل | `docs/product/schema-todos.md` | چیزهایی که جدول دارد ولی منطق کامل بعداً است |
| ADR | `docs/adr/000N-….md` | چرا این تکنولوژی |
| راهنما | `docs/guides/*.md` | نصب، شروع، تست، امنیت، همکاری، مدیر محصول |
| پرامپت سازنده | `docs/prompts/next-coding-prompt.md` | پرامپت کپی‌کردنی مرحلهٔ بعد |
| README ریشه | کوتاه | لینک زنده + شروع سریع |

### قواعد نوشتن docs
1. هر تصمیم مهم چت → همان روز در docs.
2. سند زنده (`roadmap-status`) بعد از هر مرحلهٔ تأییدشده عوض شود.
3. تعارض ماکت با قوانین کسب‌وکار → **قوانین مقدم است**.
4. برای صاحب غیرفنی: اصطلاح سخت را اول به زبان آدمیزاد بگو.

### خروجی
چند هفته بعد لازم نباشد از حافظه حدس بزنی «چرا این‌طور شد».

## فاز ۴ — مشخصات محصول (Specification) به ترتیب درست

در Gym سه لایهٔ مشخصات داشتی؛ قاطی‌شان نکن:

### ۴٫۱ مشخصات تجربه / پروتوتایپ
- چه صفحه‌هایی هست، چه حسی، چه جریان‌های نمایشی
- فایل نمونه: مشخصات پروتوتایپ

### ۴٫۲ ADR (تصمیم معماری)
برای هر انتخاب بزرگ یک ADR کوتاه:
- فرانت چیست؟
- بک چیست؟
- دیتابیس چیست؟
- سایت اول یا اپ؟ PWA کی؟

قالب: زمینه → تصمیم → دلایل → عواقب → گزینه‌های ردشده → وضعیت Accepted.

### ۴٫۳ قوانین کسب‌وکار (مهم‌ترین مشخصات رفتار)
با پرسش از صاحب محصول قفل شد، مثلاً:
- نقش‌ها و دسترسی
- فیلدهای عضو / ممنوعیت حذف سخت
- پول، بدهی، تمدید، رسید
- حضور، کلاس، کمد، پیامک/درگاه placeholder

**روش کار:** چند دور سؤال → ثبت در `business-rules.md` → ساخت بعدی فقط از روی همین.

### ۴٫۴ قرارداد پروژه (DoD و قوانین رسمی)
مثل `project-rules.md`:
- Definition of Done
- مرز پروتوتایپ/محصول
- پول و audit
- برش عمودی
- seed اجباری
- پیشوند API
- بکاپ قبل از دادهٔ واقعی

### ۴٫۵ امنیت به‌عنوان مشخصات
مثل `security.md`: سرور مرجع مجوز است، hash رمز، cookie، rate limit، چک‌لیست قبل از واقعی شدن.

### خروجی
سازنده حدس کمتری می‌زند؛ پرامپت‌ها کوتاه‌تر ولی دقیق‌تر می‌شوند چون منبع حقیقت فایل است.

## فاز ۷ — دروازهٔ تست و انتشار (از همین‌جا به بعد همیشگی)

### قانون Gym (کپی کن)
1. هر قابلیت مهم → تست خودکار
2. قبل از commit/push → اجرا کن
3. فقط اگر سبز → push
4. به صاحب بگو: **کاملاً OK** یا **ناقص** + دلیل
5. تغییر فقط-docs → تست اجباری نیست؛ بگو «فقط docs»

### کجا چه تستی؟
| لایه | ابزار نمونه | چه چیزی را بسنج |
|------|-------------|-----------------|
| API | pytest + TestClient | happy path + 401/403 + قیود کسب‌وکار |
| UI | vitest (+ Testing Library) | رندر مسیر مهم، فرم ورود ساده |
| داده | تست migration/seed/قید | موبایل یکتا، مبلغ منفی ممنوع، بدهی |

### الگوی تست هر برش عمودی
- بدون لاگین → 401
- نقش اشتباه → 403
- یک مسیر موفق
- حداقل یک لبهٔ قوانین (تکراری، منقضی، بدهی، …)

### خروجی
«کار کرد روی لپ‌تاپ من» دیگر معیار تمام‌شدن نیست.

## فاز ۸ — قوانین seed / دادهٔ ساختگی

### قانون
هر قابلیت داده‌محور باید با دادهٔ **ساختگی سازگار** دیده شود.
- نام جعلی، نه PII واقعی
- وضعیت‌های متنوع (فعال / نزدیک انقضا / بدهی)
- هرگز دادهٔ واقعی عضو در گیت/seed

### خروجی
داشبورد خالی، حس «خراب است» نمی‌دهد.

## فاز ۹ — formal کردن مدیر محصول (دو چت)

### چرخهٔ اجباری
1. چت **مدیر محصول**: کجاییم؟ بعد چیست؟ چه کار نکنم؟ پرامپت کامل بده.
2. چت **سازندهٔ جدید**: فقط همان پرامپت.
3. تست سبز + push.
4. برگشت به مدیر: «مرحله انجام شد».
5. مدیر docs و پرامپت بعدی را عوض کند.

### پرامپت سازنده باید داشته باشد
- نقش + «docs را خودت بخوان»
- هدف یک برش
- داخل / خارج محدوده
- قوانین کسب‌وکار مرتبط (متن کوتاه داخل پرامپت)
- تست + ممنوعیت `.env` در گیت
- گزارش OK/ناقص

### فایل‌های زنده
- `roadmap-status.md`
- `prompts/next-coding-prompt.md`

### خروجی
نقشه گم نمی‌شود؛ چت سازنده تبدیل به انبار تصمیم‌های پراکنده نمی‌شود.

3. اسکریپت seed

### خروجی

## فاز ۱۱ — احراز هویت و نقش سمت سرور

### حداقل
- لاگین کارکنان (یا نقش‌های همان محصول)
- hash قوی رمز
- نشست قابل‌باطل‌شدن (ترجیحاً cookie HttpOnly)
- `me` + وابستگی نقش
- تست 401/403
- حداقل UI ورود
- seed با همان الگوریتم hash واقعی

### قانون
مخفی کردن دکمه در UI ≠ امنیت.

### خروجی
برش‌های بعدی می‌توانند «پشت لاگین» امن باشند.

## فاز ۱۲ — برش‌های عمودی (Vertical Slices)

هر برش = یک جریان کامل کوچک:

```text
مدل/قانون موجود → API → تست → seed در صورت نیاز → حداقل UI → docs → commit/push
```

### ترتیب نمونه‌ای Gym (قابل الگوبرداری)
1. لیست/ثبت موجودیت اصلی (عضو)
2. عملیات روزانه (حضور)
3. پول و تمدید + audit
4. قابلیت‌های بعدی به ارزش روزانه (کلاس، کمد، …)
5. پنل کاربر نهایی وقتی کارکنان پایدار شد
6. سفت‌کاری دیپلوی

### داخل هر برش مستند کن
- چگونه امتحان شود (`getting-started`)
- چه چیزی عمداً ساخته نشد
- حفره‌های باز (schema-todos / roadmap)

### خروجی
هر هفته یک ارزش واقعی قابل‌دمو؛ نه ۲۰ صفحهٔ پوچ.

## فاز ۱۳ — پول و رویدادهای حساس

وقتی به پول/نقش/عضویت رسیدی:
- مبلغ توافقی روی همان رکورد؛ بازنویسی تاریخچه با تغییر قیمت ممنوع
- درآمد ≠ بدهی
- پرداخت ویرایش نشود → برگشت + ردیف جدید
- audit: چه کسی، چه زمانی، چه چیزی
- رسید یکتا در صورت نیاز محصول

### خروجی
مسیر مالی قابل دفاع و قابل ردیابی.

## فاز ۱۵ — انتشار: دو معنای مختلف «روی GitHub»

| نوع | چه چیزی روی اینترنت است؟ | مثال Gym |

## چرخهٔ روزانه (بعد از فاز ۹ همیشه)


## پرامپت استارت مدیر محصول (پروژهٔ جدید)

```text
تو مدیر محصول این پروژه‌ای. docs را خودت پیدا و بخوان.
از الگوی docs/guides/principled-project-playbook.md پیروی کن مگر سند محصول خلاف بگوید.
الان بگو: کجاییم، کدام فاز، مرحلهٔ بعد چیست، چه کار نکنم،
حفره‌های مستند/تست/امنیت چیست،
و یک پرامپت کامل کپی‌کردنی برای چت سازنده بده
(داخل/خارج محدوده، قوانین مرتبط، ساختار پوشه، تست سبز، ممنوعیت حدس و .env در گیت).
کد فیچر در این چت ننویس.
```
