# الگوی پروژهٔ اصولی (قابل‌تکرار)

**تاریخ ثبت:** ۱۴۰۴-۰۷-۲۴ (2026-10-16)  
**منبع:** جمع‌بندی چت مدیر محصول با صاحب پروژه — «چه چیزهایی باعث شد GYM CONTROL منظم جلو برود؟»  
**هدف:** برای پروژه‌های بعدی همین ترتیب را کپی کنی؛ نه لزوماً همان پشتهٔ React/FastAPI را.

این سند **الگوی کار** است. جزئیات همین باشگاه در `business-rules.md` و `roadmap-status.md` می‌ماند.

---

## چرا بعضی پروژه‌های vibe coding شل می‌شوند؟

معمولاً چون:

- همه‌چیز با هم ساخته می‌شود (لاگین + ۲۰ پنل + پول) قبل از قوانین و داده
- ماکت UI با محصول واقعی قاطی می‌شود
- «فکر کردن به مرحلهٔ بعد» و «کدنویسی» در یک چت طولانی قاطی می‌شوند
- بدون تست سبز و بدون گزارش OK/ناقص، حس «تمام شد» کاذب می‌آید

GYM CONTROL عمداً خلاف این‌ها جلو رفت.

---

## عادت‌های کلیدی (از Gym)

1. **اول حقیقت محصول، بعد کد زیاد** — رفتار کسب‌وکار نوشته شود، بعد انبار داده، بعد ورود، بعد پنل.
2. **ماکت ≠ مغازه** — دمو/پروتوتایپ جدا؛ کار واقعی فقط در لایهٔ محصول (`frontend/` + `backend/` یا معادل).
3. **دو چت جدا** — مدیر محصول = نقشه + پرامپت؛ سازنده = ساخت + تست. قاطی نشوند.
4. **هر برش تمام‌شدنی** — تست سبز + بدون رمز در گیت + گزارش «کاملاً OK یا ناقص».
5. **دادهٔ ساختگی اجباری** — سیستم خالی حس «کار نمی‌کند» می‌دهد.
6. **امنیت سمت سرور** — قایم‌کردن دکمه در UI امنیت نیست.

---

## مسیر ۱۰مرحله‌ای (برای هر پروژهٔ جدید)

| مرحله | کار | چرا |
|------:|-----|-----|
| ۱ | ایده + ماکت ساده | ببینی محصول چیست، قبل از قفل تکنولوژی |
| ۲ | پوشهٔ `docs` از روز اول | تصمیم‌ها گم نشوند |
| ۳ | قوانین محصول (رفتار) را ببند | AI حدس نزند کسب‌وکار چطور کار می‌کند |
| ۴ | ADR کوتاه: فرانت، بک، دیتابیس، نحوهٔ تحویل | بحث بی‌پایان بعدی کمتر شود |
| ۵ | اسکلت خالی + یک تست سلامت | لوله وصل شود قبل از کاشی‌کاری |
| ۶ | مدل داده + migration + seed ساختگی | انبار قبل از صندوق و ویترین |
| ۷ | ورود و نقش روی سرور | قبل از دادهٔ حساس و UI شلوغ |
| ۸ | برش‌های عمودی کوچک (یک جریان کامل) | هر بار یک ارزش واقعی |
| ۹ | پول / عملیات حساس + audit وقتی لازم شد | خطرناک‌ترین بخش را درست |
| ۱۰ | قبل از دادهٔ واقعی: HTTPS، بکاپ، چک امنیت پایه | «استفادهٔ واقعی» فقط بعد از این لایه |

**قانون طلایی ترتیب:**  
قوانین → اسکلت → داده → ورود → یک جریان واقعی → بعد بقیه.

---

## چرخهٔ روزانه با AI

1. از **مدیر محصول** بپرس: کجاییم؟ بعد چیست؟ چه کار نکنم؟ پرامپت بده.
2. پرامپت را در **چت سازندهٔ جدید** بفرست.
3. فقط اگر گفت تست سبز است، بپذیر «تمام شد».
4. برگرد به مدیر: «مرحله انجام شد».
5. تکرار.

جزئیات راهاندازی چت مدیر در همین ریپو: [product-manager.md](product-manager.md)

---

## پرامپت استارت مدیر محصول (پروژهٔ جدید)

بعد از اینکه در پروژهٔ جدید نقش/مهارت مدیر محصول و پوشهٔ `docs` را گذاشتی، این را در چت مدیر بفرست:

```text
تو مدیر محصول این پروژه‌ای. docs را خودت پیدا و بخوان.
نقشه‌ات این ترتیب است مگر سند محصول خلافش را بگوید:
قوانین محصول → اسکلت + تست سلامت → مدل/migration/seed → auth سمت سرور → یک برش عمودی کوچک → بعد بقیه.
الان بگو کجاییم، مرحلهٔ بعد چیست، چه کار نکنم،
و یک پرامپت کامل کپی‌کردنی برای چت سازنده بده
(داخل/خارج محدوده، قوانین مرتبط، تست سبز، ممنوعیت حدس).
کد فیچر در این چت ننویس.
```

پرامپت سازنده را خودت از صفر کامل ننویس؛ بگذار مدیر از docs جزئیات را دربیاورد.
