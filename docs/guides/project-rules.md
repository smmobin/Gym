# قوانین رسمی پروژه GYM CONTROL

**تاریخ ثبت:** ۱۴۰۴-۰۷-۲۲ (2026-10-14)  
**منبع:** تأیید صاحب پروژه برای اجرای همهٔ پیشنهادهای اولویت بالا و متوسط

این سند **قرارداد کاری** پروژه است. جزئیات امنیت در [security.md](security.md) است.

---

## ۱) Definition of Done — کی یک قابلیت «تمام» است؟

### یعنی چه؟
چک‌لیست تمام‌شدن کار. تا همهٔ بندها سبز نباشند، قابلیت را «تمام» اعلام نکن و به GitHub به‌عنوان فیچر کامل نفروش.

### چرا لازم است؟
در vibe coding خیلی سریع کد زیاد می‌شود. بدون DoD ممکن است:
- چیزی «کار می‌کند» ولی تست ندارد
- UI فارسی/RTL خراب شود
- رمز یا دادهٔ حساس به گیت برود
- بعداً معلوم نباشد چرا فلان تصمیم گرفته شد

### چک‌لیست DoD (اجباری)

- [ ] رفتار قابلیت مطابق نیاز همان چت/تسک است
- [ ] تست خودکار مرتبط نوشته و **سبز** شده (`docs/guides/testing.md`)
- [ ] اگر تصمیم مهم بود → در `docs/` ثبت شده
- [ ] RTL / فارسی / نمایش تومان و تاریخ شمسی در UI خراب نشده (اگر به UI دست زدی)
- [ ] هیچ رمز، `.env`، یا دادهٔ واقعی عضو وارد Git نشده
- [ ] برای API جدید: مسیر زیر `/api/v1/...` و در صورت نیاز در OpenAPI/docs قابل دیدن است
- [ ] به صاحب پروژه گزارش داده شده: **کاملاً OK** یا **ناقص/قرمز** + دلیل

---

## ۲) مرز پروتوتایپ و محصول واقعی

| لایه | کجاست؟ | نقش |
|------|--------|-----|
| **پروتوتایپ** | ریشه: `index.html`, `athlete.html`, … | فقط نمایش و مرجع طراحی Ocean Dark + GitHub Pages |
| **محصول واقعی** | `frontend/` + `backend/` + Postgres | جایی که فیچر جدید، API، تست و امنیت واقعی ساخته می‌شود |
| **تم‌های جایگزین** | `alternate-themes/` (محلی) | روی دستگاه؛ به GitHub نمی‌رود |

### قانون
- کار جدید توسعه → فقط در `frontend/` و `backend/`
- پروتوتایپ HTML را «سامانهٔ واقعی» فرض نکن (نقش‌ها نمایشی‌اند، داده در سرور نیست)
- اگر UI از پروتوتایپ کپی می‌شود، مقصد نهایی کامپوننت React است

جزئیات بیشتر در بخش توضیح مفهومی همین موضوع در چت/این سند پایین‌تر تکرار شده تا در docs بماند.

---

## ۳) ثابت‌های محصول (ایران)

- رابط: **فارسی** و **RTL** (`dir="rtl"`)
- مبلغ: **تومان** با جداکنندهٔ هزارگان
- تاریخ در UI: **شمسی** (قابل خواندن؛ تبدیل معتبر، نه دستی غلط)
- شناسه‌ها و نام متغیرهای کد: انگلیسی

این‌ها سلیقه نیستند؛ قرارداد محصول‌اند.

---

## ۴) قوانین پول و عضویت

- تغییر قیمت طرح اشتراک، **سوابق پرداخت و عضویت گذشته را عوض نکند**
- قیمت توافق‌شده در زمان تراکنش/عضویت ذخیره شود
- **درآمد** = مبلغ پرداخت‌شده؛ **بدهی** = مبلغ پرداخت‌نشده — قاطی نشوند
- هزینه‌های باشگاه (اگر بعداً آمد) جدا از درآمد ناخالص ثبت شود
- عملیات مالی مهم قابل ردگیری باشند (→ بخش audit)

---

## ۵) برش عمودی (Vertical Slice)

هر بار یک **جریان کامل** بساز، نه ۲۰ صفحهٔ خالی.

مثال درست: «ثبت عضو» = مدل DB + migration + API + تست + حداقل UI متصل  
مثال غلط: همهٔ داشبوردها بدون API

---

## ۶) قرارداد API

- پیشوند پایدار: `/api/v1`
- شکستن عمدی قرارداد بدون نسخهٔ جدید (`v2`) ممنوع
- مستند تعاملی: `/docs` فست‌اپ‌آی

---

## ۷) لاگ تغییرات مهم (Audit)

برای این رویدادها، در نسخهٔ عملیاتی جدول/لاگ `audit_logs` (یا معادل) در نظر گرفته شود:

- ایجاد/تمدید/لغو عضویت
- ثبت/برگشت پرداخت
- تغییر نقش یا دسترسی کارکنان
- تغییر تنظیمات حساس باشگاه

حداقل فیلدها: چه کسی، چه زمانی، چه چیزی، مقدار قبل/بعد (در حد لازم، بدون رمز)

---

## ۸) پشتیبان دیتابیس

قبل از ورود دادهٔ واقعی اعضا:

- حداقل یک روش بکاپ Postgres مشخص شود (حتی دستی هفتگی در شروع)
- محل نگهداری بکاپ جدا از لپ‌تاپِ تنها نباشد (در حد امکان)
- تست بازیابی یک‌بار آزمایش شود («بکاپ بدون restore بی‌فایده است»)
