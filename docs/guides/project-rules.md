## ۱) Definition of Done — کی یک قابلیت «تمام» است؟

### یعنی چه؟
چک‌لیست تمام‌شدن کار. تا همهٔ بندها سبز نباشند، قابلیت را «تمام» اعلام نکن و به GitHub به‌عنوان فیچر کامل نفروش.

### چرا لازم است؟
در vibe coding خیلی سریع کد زیاد می‌شود. بدون DoD ممکن است:
- چیزی «کار می‌کند» ولی تست ندارد
- UI فارسی/RTL خراب شود
- رمز یا دادهٔ حساس به گیت برود
- بعداً معلوم نباشد چرا فلان تصمیم گرفته شد

### چک‌لیست DoD (اجباری)

- [ ] رفتار قابلیت مطابق نیاز همان چت/تسک است
- [ ] تست خودکار مرتبط نوشته و **سبز** شده (`docs/guides/testing.md`)
- [ ] اگر قابلیت داده می‌سازد/نشان می‌دهد → **دادهٔ فیک/نمونه** قابل مشاهده اضافه یا به‌روز شده (بخش ۵٫۱)
- [ ] اگر تصمیم مهم بود → در `docs/` ثبت شده
- [ ] RTL / فارسی / نمایش تومان و تاریخ شمسی در UI خراب نشده (اگر به UI دست زدی)
- [ ] هیچ رمز، `.env`، یا دادهٔ واقعی عضو وارد Git نشده
- [ ] برای API جدید: مسیر زیر `/api/v1/...` و در صورت نیاز در OpenAPI/docs قابل دیدن است
- [ ] به صاحب پروژه گزارش داده شده: **کاملاً OK** یا **ناقص/قرمز** + دلیل

## ۲) مرز پروتوتایپ و محصول واقعی

| لایه | کجاست؟ | نقش |
|------|--------|-----|
| **پروتوتایپ** | ریشه: `index.html`, `athlete.html`, … | فقط نمایش و مرجع طراحی Ocean Dark + GitHub Pages |
| **محصول واقعی** | `frontend/` + `backend/` + Postgres | جایی که فیچر جدید، API، تست و امنیت واقعی ساخته می‌شود |
| **تم‌های جایگزین** | `alternate-themes/` (محلی) | روی دستگاه؛ به GitHub نمی‌رود |

### قانون
- کار جدید توسعه → فقط در `frontend/` و `backend/`
- پروتوتایپ HTML را «سامانهٔ واقعی» فرض نکن (نقش‌ها نمایشی‌اند، داده در سرور نیست)
- اگر UI از پروتوتایپ کپی می‌شود، مقصد نهایی کامپوننت React است

### توضیح کامل‌تر — چرا این مرز را جدی بگیریم؟

پروتوتایپ مثل **ماکت فروشگاه** است: قفسه‌ها قشنگ‌اند، ولی پول واقعی جابه‌جا نمی‌شود و قفل انبار واقعی نیست.  
محصول واقعی مثل **فروشگاه باز** است: موجودی در انبار (Postgres)، صندوق (API)، و نگهبان (احراز هویت).

اگر وسط راه یک قابلیت را در HTML بسازی و یکی را در React، بعداً:

- نمی‌فهمی کدام نسخه حقیقت است
- تست‌ها روی چیز اشتباه نوشته می‌شوند
- ممکن است فکر کنی «نقش منشی امن است» در حالی که فقط دکمه قایم شده

**قانون طلایی:** از این لحظه هر فیچر جدید فقط در محصول واقعی (`frontend` + `backend`).

## ۲٫۱) توضیح کامل Definition of Done

### مثال روزمره
فرض کن می‌گویی «ثبت عضو آماده است». بدون DoD ممکن است فقط فرم React باشد بدون ذخیره در دیتابیس. با DoD مجبوری بگویی:

1. API ثبت عضو هست؟  
2. در Postgres ذخیره می‌شود؟  
3. تست سبز است؟  
4. منشی بدون لاگین نمی‌تواند ثبت کند؟  
5. به صاحب پروژه گفته‌ای کاملاً OK است یا نه؟

اگر حتی یکی قرمز باشد، قابلیت «تمام» نیست — حتی اگر در دمو قشنگ به نظر برسد.

### چه چیزی DoD نیست؟
- «روی لپ‌تاپ من یک‌بار کار کرد»
- «UI قشنگ شد»
- «فردا تست می‌نویسم»

## ۲٫۲) نقشهٔ راه — کدام کار را اول انجام بده؟

ترتیب پیشنهادی بعد از تأیید این قوانین (از بالا به پایین برو؛ همزمان همه را شروع نکن):

| مرحله | کار | چرا اول؟ |
|------:|-----|----------|
| **۰** | همین قوانین + امنیت را در docs بخوان و قبول کن | قرارداد کار |
| **۱** | مدل‌های دیتابیس + اولین migration (اعضا، طرح، عضویت، حضور، پرداخت) | بدون دادهٔ ساخت‌یافته API پوچ است |
| **۲** | احراز هویت واقعی + نقش‌ها سمت سرور + تست 401/403 | قبل از دادهٔ واقعی و قبل از UI پیچیده |
| **۳** | اولین برش عمودی: مثلاً «لیست/ثبت عضو» API + UI + تست | اولین ارزش واقعی محصول |
| **۴** | حضور و غیاب | جریان روزانهٔ منشی |
| **۵** | تمدید اشتراک + ثبت پرداخت + قوانین پول + شروع audit | پول = حساس‌ترین بخش |
| **۶** | پنل ورزشکار (فقط دادهٔ خودش) | جداسازی دسترسی |
| **۷** | گزارش مدیر + تنظیمات | بعد از اینکه داده درست وارد می‌شود |
| **۸** | دیپلوی HTTPS + بکاپ + اسکن امنیتی پلتفرم‌ها | قبل از استفادهٔ باشگاه واقعی |
| **۹** | PWA (اختیاری، طبق ADR 0004) | بعد از پایدار شدن وب |

**الان کجا ایستاده‌ای؟** اسکلت فرانت/بک و Postgres آماده‌اند → مرحلهٔ منطقی بعدی = **۱ (مدل‌ها و migration)**.

تا صاحب پروژه صریحاً نگوید «برو مدل‌ها را بساز»، فقط مستندسازی/قوانین جلو می‌رود.

## ۳) ثابت‌های محصول (ایران)

- رابط: **فارسی** و **RTL** (`dir="rtl"`)
- مبلغ: **تومان** با جداکنندهٔ هزارگان
- تاریخ در UI: **شمسی** (قابل خواندن؛ تبدیل معتبر، نه دستی غلط)
- شناسه‌ها و نام متغیرهای کد: انگلیسی

این‌ها سلیقه نیستند؛ قرارداد محصول‌اند.

---

## ۴) قوانین پول و عضویت

- تغییر قیمت طرح اشتراک، **سوابق پرداخت و عضویت گذشته را عوض نکند**
- قیمت توافق‌شده در زمان تراکنش/عضویت ذخیره شود
- **درآمد** = مبلغ پرداخت‌شده؛ **بدهی** = مبلغ پرداخت‌نشده — قاطی نشوند
- هزینه‌های باشگاه (اگر بعداً آمد) جدا از درآمد ناخالص ثبت شود
- عملیات مالی مهم قابل ردگیری باشند (→ بخش audit)

## ۵) برش عمودی (Vertical Slice)

هر بار یک **جریان کامل** بساز، نه ۲۰ صفحهٔ خالی.

مثال درست: «ثبت عضو» = مدل DB + migration + API + تست + دادهٔ فیک + حداقل UI متصل  
مثال غلط: همهٔ داشبوردها بدون API

## ۵٫۱) دادهٔ فیک / نمونه (Seed) — اجباری برای دیدن کار سیستم

**تاریخ افزودن قانون:** به درخواست صاحب پروژه — ۱۴۰۴-۰۷-۲۳

### یعنی چه؟
**دادهٔ فیک** یعنی اعضای ساختگی، پرداخت نمونه، حضور نمونه و … که واقعی نیستند، ولی سیستم را «پر» نشان می‌دهند تا صاحب پروژه ببیند محصول چطور کار می‌کند.

### چرا اجباری است؟
بدون داده، داشبورد و جدول‌ها خالی‌اند و حس «کار نمی‌کند» می‌دهد — حتی اگر کد درست باشد.

### قوانین

1. برای هر قابلیت مهم که داده نشان می‌دهد یا ذخیره می‌کند، باید راهی برای **دیدن دادهٔ نمونه** وجود داشته باشد (اسکریپت seed، فیکسچر تست، یا endpoint/دستور توسعه).
2. داده‌ها **ساختگی** باشند (نام‌هایی مثل علی رضایی، سارا محمدی — نه اطلاعات واقعی افراد).
3. داده‌ها با هم **سازگار** باشند (مثلاً جمع پرداخت‌ها با کارت داشبورد یکی باشد).
4. وضعیت‌های متنوع داشته باشند: اشتراک فعال / نزدیک به انقضا / منقضی، بدهی، حضور متفاوت.
5. مبالغ به تومان؛ تاریخ‌ها در UI شمسی و خوانا.
6. Seed فقط برای محیط توسعه/دمو؛ هرگز دادهٔ واقعی عضو را به‌عنوان seed در گیت نگذار.
7. محل پیشنهادی بعدی در کد: مثلاً `backend/app/db/seed.py` یا دستور `python -m app.db.seed` + توضیح در `docs/guides/getting-started.md`.

### حداقل پیشنهادی وقتی مدل‌ها آماده شد
حدود ۸ عضو نمونه + چند طرح اشتراک + چند حضور + چند پرداخت — هم‌راستا با مشخصات پروتوتایپ در `docs/product/`.

- شکستن عمدی قرارداد بدون نسخهٔ جدید (`v2`) ممنوع

## ۷) لاگ تغییرات مهم (Audit)

برای این رویدادها، در نسخهٔ عملیاتی جدول/لاگ `audit_logs` (یا معادل) در نظر گرفته شود:

- ایجاد/تمدید/لغو عضویت
- ثبت/برگشت پرداخت
- تغییر نقش یا دسترسی کارکنان
- تغییر تنظیمات حساس باشگاه

حداقل فیلدها: چه کسی، چه زمانی، چه چیزی، مقدار قبل/بعد (در حد لازم، بدون رمز)

---

## ۸) پشتیبان دیتابیس

قبل از ورود دادهٔ واقعی اعضا:

- حداقل یک روش بکاپ Postgres مشخص شود (حتی دستی هفتگی در شروع)
- محل نگهداری بکاپ جدا از لپ‌تاپِ تنها نباشد (در حد امکان)
- تست بازیابی یک‌بار آزمایش شود («بکاپ بدون restore بی‌فایده است»)
