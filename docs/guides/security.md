# امنیت پروژه GYM CONTROL

**تاریخ ثبت:** ۱۴۰۴-۰۷-۲۲ (2026-10-14)  
**هدف:** امنیت «بالا و قابل‌اتکا» برای سامانهٔ باشگاه (اعضا، پرداخت، نقش‌ها) — نه حس امنیت کاذب فقط با قشنگ بودن UI.

---

## ۱) امنیت یعنی چه؟ (ساده)

امنیت یعنی:

1. **فقط آدم درست** به دادهٔ درست برسد (ورزشکار مال خودش؛ منشی/مدیر طبق نقش)
2. **داده‌ها درست و قابل اعتماد بمانند** (پرداخت جعلی/دستکاری نشود)
3. **سیستم در دسترس بماند** (خراب یا قفل نشود بی‌دلیل)
4. اگر حمله/اشتباهی شد، **بتوان فهمید چه شده** (لاگ)

در باشگاه، حساس‌ترین‌ها معمولاً: شماره موبایل اعضا، سوابق مالی، دسترسی منشی/مدیر.

---

## ۲) اصول اجباری این پروژه

### ۲.۱ سرور مرجع حقیقت است (نه فرانت)

- مخفی کردن دکمه در React **امنیت نیست**
- نقش کاربر، مجوز API، و فیلتر «فقط دادهٔ خودش» باید در **FastAPI** enforce شود
- انتخاب‌گر نقش پروتوتایپ HTML هرگز وارد محصول واقعی نشود

### ۲.۲ احراز هویت و نشست

وقتی لاگین واقعی ساخته شد:

- رمز عبور: فقط **hash** قوی (مثلاً Argon2 / bcrypt) — هرگز متن خام در DB
- ترجیح پنل وب: **cookie با HttpOnly + Secure + SameSite** (یا طرح معادل امن)
- JWT در `localStorage` برای پنل حساس توصیهٔ اول نیست (دزدیده‌شدن با XSS آسان‌تر است)
- محدودیت تلاش ورود (rate limit) روی `/login`
- خروج واقعی = باطل‌کردن نشست سمت سرور

### ۲.۳ کنترل دسترسی (Authorization)

نقش‌های پایه: `member` / `receptionist` / `trainer` / `manager`

| نقش | اصل |
|-----|-----|
| ورزشکار | فقط دادهٔ خودش |
| منشی | عملیات روزمرهٔ اعضا/حضور/پرداخت طبق سیاست باشگاه |
| مدیر | گزارش و تنظیمات؛ باز هم هر endpoint باید چک نقش شود |

هر endpoint جدید: صریحاً بگو «کی اجازه دارد؟» و در تست هم یک مورد «بدون مجوز → 401/403» بگذار.

### ۲.۴ ورودی‌ها و تزریق

- همهٔ ورودی‌ها با Pydantic اعتبارسنجی شوند
- SQL فقط از طریق ORM/پارامتریک (SQLAlchemy) — رشتهٔ SQL خام با ورودی کاربر ممنوع
- آپلود فایل (اگر بعداً آمد): نوع/حجم محدود، نام امن، خارج از مسیر اجرایی

### ۲.۵ اسرار و پیکربندی

- `.env` فقط محلی؛ در گیت نباشد (همین الان در `.gitignore` است)
- رمز DB، کلید نشست، و بعداً درگاه/پیامک فقط در محیط امن
- برای production: HTTPS اجباری
- چرخش رمزها اگر لو رفتند

### ۲.۶ داده و حریم خصوصی

- در توسعه از دادهٔ ساختگی استفاده کن
- حداقل داده را نگه دار (نیاز نیست کد ملی واقعی در MVP)
- بکاپ رمزدار/محافظت‌شده
- سیاست نگهداری: پرداخت‌ها را بی‌دلیل پاک نکن؛ لاگ دسترسی محدود باشد

### ۲.۷ پول

- تغییر سوابق پرداخت فقط با مسیر کنترل‌شده + audit
- مبلغ و وضعیت از سمت کلاینت «قابل اعتماد مطلق» نیست؛ سرور محاسبه/اعتبارسنجی کند

### ۲.۸ وابستگی‌ها (Supply chain)

- مرتب به‌روزرسانی `requirements.txt` / `package-lock.json`
- آسیب‌پذیری‌های شناخته‌شده را پیگیری کن (Dependabot / pip-audit / npm audit)

## ۳) استانداردها و چک‌لیست‌های بین‌المللی (مرجع)

این‌ها «پلتفرم/استاندارد» رایجی هستند که پروژه‌های جدی با آن‌ها خود را می‌سنجند:

| نام | چیست؟ | برای ما چه کاربردی دارد؟ |
|-----|--------|---------------------------|
| **OWASP Top 10** | ۱۰ ریسک رایج وب | چک‌لیست طراحی API و فرانت |
| **OWASP ASVS** | سطح‌بندی نیازمندی‌های امنیتی | برای سخت‌گیری تدریجی (سطح ۱ → ۲) |
| **OWASP API Security Top 10** | ریسک‌های مخصوص API | مستقیماً به FastAPI مربوط است |
| **CWE / SANS Top 25** | ضعف‌های نرم‌افزاری رایج | هنگام بازبینی کد |
| **NIST CSF** (اختیاری) | چارچوب مدیریت ریسک | برای بلوغ سازمانی بعداً |

هدف اولیهٔ این پروژه: پوشش عملی **OWASP Top 10 + API Top 10** در حد MVP باشگاه، نه گواهی‌نامهٔ سازمانی سنگین از روز اول.

## ۴) ابزارها و پلتفرم‌های تست امنیت

### ۴.۱ روی خود ریپو / CI (پیشنهادی زود)

| ابزار | کار |
|--------|-----|
| **GitHub Dependabot** | هشدار پکیج‌های آسیب‌پذیر |
| **GitHub CodeQL** | اسکن استاتیک کد در Actions |
| **npm audit** | آسیب‌پذیری وابستگی فرانت |
| **pip-audit** / `safety` | آسیب‌پذیری وابستگی پایتون |
| **تست‌های pytest خودمان** | 401/403 و مرز دسترسی |

### ۴.۲ اسکنر وب و هدرها (وقتی دامنه/HTTPS واقعی داری)

| پلتفرم / ابزار | آدرس تقریبی / نام | چه می‌گوید؟ |
|----------------|-------------------|-------------|
| **Mozilla Observatory** | observatory.mozilla.org | هدرها و پیکربندی امنیتی سایت |
| **Security Headers** | securityheaders.com | نمرهٔ HTTP security headers |
| **SSL Labs (SSL Test)** | ssllabs.com/ssltest | کیفیت TLS/HTTPS |
| **OWASP ZAP** | zaproxy.org | اسکن آسیب‌پذیری وب (داینامیک) |
| **Burp Suite** (حرفه‌ای) | portswigger.net | تست دستی/نیمه‌خودکار |

### ۴.۳ نکتهٔ مهم اخلاقی/قانونی

- فقط روی **دارایی خودت** یا با مجوز اسکن کن (همین ریپو / دامنهٔ خودت)
- اسکن سنگین روی سایت دیگران یا بدون مجوز غیرقانونی/غیراخلاقی است
- GitHub Pages استاتیک فعلی ≠ سامانهٔ لاگین‌دار؛ نمرهٔ Observatory قبل از API واقعی انتظار معجزه ندارد

### ۴.۴ برنامهٔ پیشنهادی برای GYM CONTROL

**فاز الان (اسکلت):**  
npm audit + pip-audit گاه‌به‌گاه؛ تست دسترسی وقتی endpoint نقش‌دار آمد؛ Dependabot روی GitHub.

**فاز API واقعی روی دامنه:**  
HTTPS → SSL Labs + Security Headers + Mozilla Observatory → ZAP baseline روی staging (نه بی‌محابا روی production با دادهٔ واقعی).

**فاز پول/پیامک:**  
بازبینی OWASP ASVS سطح مناسب + audit مالی + سخت‌گیری secrets.

## ۵) مسیر «امنیت خیلی بالا» برای این پروژه (لایه‌ای)

امنیت یک‌شبه نیست؛ لایه‌لایه ساخته می‌شود. هدف نهایی برای GYM CONTROL:

### لایه A — پایه (قبل از هر دادهٔ واقعی)
1. لاگین واقعی + hash رمز (Argon2/bcrypt)
2. مجوز سمت سرور برای هر endpoint + تست منفی
3. HTTPS در اینترنت
4. `.env` و اسرار خارج از گیت
5. CORS محدود
6. بکاپ Postgres + یک‌بار restore

### لایه B — سخت‌گیری باشگاه
1. Rate limit ورود و APIهای مالی
2. Audit برای عضویت/پرداخت/نقش
3. جداسازی ورزشکار از دادهٔ دیگران (حتی با دستکاری `member_id` در درخواست)
4. هدرهای امنیتی (CSP در حد معقول، HSTS، …)
5. Dependabot + npm audit + pip-audit روتین

### لایه C — بلوغ بالا (وقتی باشگاه واقعی استفاده می‌کند)
1. محیط staging جدا از production
2. اسکن OWASP ZAP روی staging
3. بازبینی OWASP API Top 10 روی endpointهای پول
4. چرخش کلیدها/رمزها و سیاست دسترسی کارکنان
5. مانیتور خطا بدون نشت جزئیات داخلی به کلاینت

**قانون:** تا لایه A کامل نشده، دادهٔ واقعی عضو وارد سیستم نشود.

## ۷) تعهد Agent: اسکن امنیتی وقتی فاز امنیت تکمیل شد

وقتی صاحب پروژه گفت امنیت پایه (لایه A یا چک‌لیست بالا) کامل شده، Agent باید **خودش** این بررسی‌ها را در حد دسترسی محیط انجام دهد و نتیجه را فارسی/واضح گزارش کند:

1. `npm audit` در `frontend/`
2. `pip-audit` (یا معادل) در `backend/`
3. مرور تست‌های دسترسی (401/403) اگر موجودند
4. اگر دامنهٔ HTTPS آماده بود: پیشنهاد/اجرای چک با **Mozilla Observatory** و **SSL Labs** و در صورت امکان **Security Headers**
5. اگر staging آماده بود: یادآوری یا کمک برای **OWASP ZAP** baseline

نتیجهٔ گزارش باید بگوید: **قابل قبول برای استفادهٔ واقعی** یا **هنوز نه** + لیست مشکل‌ها.
