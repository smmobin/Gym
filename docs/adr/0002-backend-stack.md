# ADR 0002 — پشتهٔ بک‌اند

- **وضعیت:** Accepted  
- **تاریخ:** 2026-10-13  
- **مرتبط:** [0001 فرانت](0001-frontend-stack.md) · [0003 دیتابیس](0003-database.md)

## زمینه

پروتوتایپ فعلی بک‌اند ندارد. برای نسخهٔ واقعی نیاز داریم به:

- احراز هویت و نشست امن
- کنترل دسترسی بر اساس نقش (ورزشکار / منشی / مدیر / مربی)
- API برای اعضا، اشتراک، حضور، پرداخت، گزارش
- اعتبارسنجی سمت سرور (فرانت به‌تنهایی امن نیست)
- آمادگی برای اتصال بعدی به پیامک / درگاه پرداخت

سؤال صریح: **آیا پایتون برای بک‌اند خوب است؟**

## تصمیم (پیشنهاد اصلی)

**بک‌اند پیشنهادی: Python + FastAPI**

| بخش | انتخاب |
|-----|--------|
| زبان | Python 3.12+ |
| فریمورک | **FastAPI** |
| اعتبارسنجی مدل | Pydantic |
| ORM | SQLAlchemy 2 + Alembic (مهاجرت) |
| احراز هویت | JWT یا session cookie امن (ترجیح: cookie httpOnly برای پنل وب) |
| قرارداد API | OpenAPI خودکار FastAPI |

### آیا پایتون خوب است؟

**بله — برای این پروژه انتخاب قوی و معقولی است**، به‌شرطی که API-محور بسازید (نه قالب HTML سمت سرور).

چرا پایتون / FastAPI اینجا می‌خورد:

1. **سرعت توسعهٔ API** — تعریف endpoint، اعتبارسنجی و مستند OpenAPI خیلی سریع جلو می‌رود.
2. **خوانایی و استخدام** — خیلی از تیم‌ها و فریلنسرها پایتون بلدند.
3. **مناسب دامنهٔ باشگاه** — منطق عضویت، گزارش مالی ساده، کرون جاب (هشدار انقضای اشتراک) بدون دردسر نوشته می‌شود.
4. **اکوسیستم دیتا** — اگر بعداً گزارش‌گیری یا اسکریپت‌های مدیریتی بخواهید، پایتون راحت است.

چه موقع پایتون *بهترین* نیست:

- اگر بخواهید **یک زبان واحد** فرانت و بک (TypeScript همه‌جا) داشته باشید → NestJS / Hono بهتر است.
- اگر تیم شما اصلاً پایتون بلد نباشد و فقط JS/TS بلد باشد → همان را انتخاب کنید تا سرعت تیم نیفتد.

### پیشنهاد جایگزین (اگر TypeScript را ترجیح می‌دهید)

**Node.js + NestJS** (یا Hono برای سبک‌تر بودن)

- یک زبان با React
- اشتراک‌گذاری تایپ‌ها بین فرانت و بک ممکن است
- کمی boilerplate بیشتر از FastAPI در NestJS

**نظر نهایی نویسندهٔ این ADR:** برای GYM CONTROL با اولویت «سایت واقعی + API تمیز + تیم کوچک»، **FastAPI را پیشنهاد می‌کنم**. اگر شما یا همکارتان فقط TypeScript مسلطید، NestJS را بدون عذاب وجدان انتخاب کنید — هر دو برای این مقیاس کافی‌اند. «بک‌اند بهتر مطلق» وجود ندارد؛ بهتر یعنی *با تیم و مسیر محصول شما جور دربیاید*.

## دلایل انتخاب FastAPI نسبت به گزینه‌های پایتونی دیگر

| گزینه | نظر |
|--------|------|
| **FastAPI** | پیشنهاد اصلی — مدرن، سریع، OpenAPI، async |
| Django + DRF | عالی برای ادمین آماده و مونولیت بزرگ؛ برای API خالص کمی سنگین‌تر است |
| Flask | سبک است ولی خودتان باید خیلی چیزها را جمع کنید |
| .NET / Go | قوی‌اند؛ برای شروع این محصول معمولاً هزینهٔ یادگیری/راه‌اندازی بی‌دلیل است |

## عواقب

**مثبت**

- مرز امنیتی درست: مجوزها و پول سمت سرور
- مستند API رایگان از OpenAPI
- تست‌پذیری خوب endpointها

**منفی / هزینه**

- باید هاست جدا برای API (VPS، Railway، Fly.io، لیارا، ابرآروان و مشابه)
- CORS و استقرار دو بخشی (فرانت استاتیک + API)
- تیم باید با Python راحت باشد

## مرزهای عمدی (فعلاً نساز)

- پرداخت آنلاین واقعی
- پیامک واقعی
- اپ اندروید بومی
- میکروسرویس زیاد — یک سرویس مونولیت ماژولار کافی است
