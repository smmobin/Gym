# پرامپت‌های سازنده — دو برش پشت‌سرهم

آخرین به‌روزرسانی: ۱۴۰۴-۰۷-۲۷ (مدیر محصول)  
صاحب پروژه: **اول پرامپت A** را در چت سازنده بفرست؛ بعد از «انجام شد» و تأیید مدیر محصول، **پرامپت B**.

---

## پرامپت A — ورود یکپارچه + رفع باگ نقش + پنل مربی

```text
# نقش
تو Agent سازندهٔ GYM CONTROL هستی (نه مدیر محصول).
docs را از docs/README.md خودت پیدا کن. منبع حقیقت نقش‌ها: docs/product/business-rules.md (+ prototype برای ظاهر Ocean Dark).
کار در frontend/ + backend/. ظاهر محصول = MPA Ocean Dark فعلی (ADR 0005). React برنگردان.

# مشکل‌های گزارش‌شدهٔ صاحب (باید حل شوند)
1) انتخاب نقش از کارت‌های پایین لندینگ / انتخاب دستی «منشی یا مدیر یا ورزشکار» روی UI ورود پذیرفته نیست.
2) کاربر فقط موبایل+رمز می‌دهد؛ سامانه باید بفهمد ورزشکار است یا منشی یا مدیر یا مربی و به پنل درست ببرد.
3) باگ: ورود با اطلاعات «منشی» عملاً پنل/نقش مدیر می‌دهد.
   ریشهٔ محتمل (تأیید کن و درست کن): در `frontend/login/index.html` فیلد موبایل پیش‌فرض `09120000001` (= مدیر در seed) است؛ کاربر با رمز مشترک وارد می‌شود و مدیر می‌شود. همچنین لینک‌های لندینگ ممکن است گمراه‌کننده باشند.
4) باید حساب‌های دموی واضح برای نقش‌ها باشد (حداقل مدیر / منشی / مربی / ورزشکار) با موبایل‌های متفاوت در seed + راهنمای کوتاه روی صفحهٔ ورود (بدون پر کردن خودکار فقط شمارهٔ مدیر).
5) نقش مربی باید پنل واقعی داشته باشد (الان trainer به `/receptionist/#workouts` پرتاب می‌شود — کافی نیست).

# هدف پرامپت A
## الف) ورود یکپارچه (بدون انتخاب نقش)
- یک صفحهٔ ورود واحد (مثلاً `/login/`) با فقط موبایل + رمز.
- از لندینگ: یک CTA «ورود به سامانه» → همان صفحه؛ کارت‌های جداگانهٔ ورزشکار/منشی/مدیر در پایین `#roles` را بردار یا به همان یک لینک تبدیل کن.
- صفحهٔ جدا `/athlete/login.html` را حذف یا به `/login/` ریدایرکت کن (دیگر دو درگاه ورود عمومی نباشد).
- سرور باید نقش را تشخیص دهد — نه کلاینت با حدس UI:
  - ترجیح: endpoint یکپارچه مثل `POST /api/v1/auth/login` (یا مسیر جدید واضح) که اول جدول کارکنان (`users`) را چک کند؛ اگر نبود جدول عضو (`members` با password_hash) را چک کند؛ کوکی درست را ست کند (`gym_session` یا `gym_athlete_session`)؛ در پاسخ `kind` + `role` (+ دادهٔ لازم) برگرداند.
  - اگر موبایل در هر دو جدول بود: اولویت کارکنان؛ در docs/تست ثبت کن.
  - بعد از موفقیت: redirect به پنل:
    - manager → `/manager/`
    - receptionist → `/receptionist/`
    - trainer → `/trainer/` (جدید)
    - athlete → `/athlete/`
- هیچ radio/dropdown انتخاب نقش روی فرم ورود نباشد.
- rate limit ورود حفظ شود.

## ب) رفع باگ منشی→مدیر + seed/راهنما
- پیش‌فرض موبایل مدیر روی input را بردار (خالی یا placeholder خنثی).
- روی UI ورود، جدول کوچک دمو (فقط dev/seed) نشان بده:
  - مدیر: 09120000001
  - منشی: 09120000002
  - مربی: 09120000003 (یا هرچه seed است)
  - ورزشکار: 09121111001
  - رمز مشترک seed فعلی را بنویس (همان DEV_* موجود) — بدون گذاشتن secret جدید در گیت.
- تست: لاگین 09120000002 → نقش receptionist و URL پنل منشی؛ 09120000001 → manager؛ مربی → trainer؛ ورزشکار → athlete.
- اگر بعد از لاگین منشی هنوز UI مدیر می‌بیند، گیت نقش روی صفحات manager/receptionist را هم درست کن (`requireStaff`).

## ج) پنل مربی (از docs — اگر مبهم بود از صاحب بپرس؛ حدس نزن)
طبق business-rules پیاده کن؛ ظاهر Ocean Dark هم‌سبک منشی/مدیر.

مربی می‌تواند:
- فقط شاگردهای خودش را ببیند (لیست تخصیص مربی موجود)
- برای همان‌ها برنامهٔ تمرینی بنویسد/ویرایش کند (API workout_plans موجود را reuse)
- برای شاگرد خودش حضور/ورود ثبت کند (نوع جلسه مربی در صورت پشتیبانی API)
- داشبورد سادهٔ شاگردان خودش

مربی نباید:
- گزارش مالی مدیر، تنظیمات باشگاه (PATCH)، مدیریت همهٔ اعضا، کمد همه، هزینه‌ها، ساخت کاربر کارکنان
- دیدن عضو غیرشاگرد (سرور 403؛ مخفی کردن UI کافی نیست)

صفحه: `frontend/trainer/index.html` (+ JS مربوطه). `panelPathForRole('trainer')` → `/trainer/`.
seed: حداقل یک مربی با چند شاگرد تخصیص‌داده‌شده fore دمو.

اگر موردی در docs نیست و برای قفل دسترسی لازم است، قبل از اختراع قانون در گزارش از صاحب بپرس؛ برای موارد داخل business-rules همان را اجرا کن.

## تست و DoD
- pytest: لاگین یکپارچه (staff هر نقش + athlete + رمز غلط + اولویت staff اگر تداخل)
- فرانت: تست دود ورود بدون انتخاب نقش + redirect نقش‌ها
- pytest/فرانت: منشی دیگر به پنل مدیر نرود
- پنل مربی: دسترسی محدود شاگرد + 403 برای عضو دیگران
- getting-started: جدول حساب‌های دمو + مسیر `/login/` واحد
- business-rules/roadmap را با «ورود یکپارچه بدون انتخاب نقش» هم‌خوان کن
- تست سبز → commit/push طبق قانون Gym
- گزارش: OK یا ناقص + علت باگ منشی و نحوهٔ تست دستی

# خارج از محدودهٔ A
- درگاه پرداخت واقعی، پیامک واقعی
- بازگرداندن React
- دیپلوی با credential صاحب
```

## پرامپت B — ادامهٔ محصول بعد از A (درگاه پرداخت sandbox)

فقط وقتی A سبز و تأیید شد بفرست.

```text
# نقش
تو Agent سازندهٔ GYM CONTROL هستی. docs را از docs/README.md بخوان.
فرض: پرامپت A (ورود یکپارچه + پنل مربی) انجام شده. کار در frontend/ + backend/. Ocean Dark MPA. بدون React. secrets در گیت نرود.

# هدف
اتصال امن درگاه پرداخت آنلاین ایرانی (پیشنهاد: زرین‌پال) در حالت sandbox، طبق business-rules:
- ورزشکار لاگین‌شده بتواند برای تمدید/بدهی خودش پرداخت online شروع کند.
- پس از verify سروری موفق: پرداخت paid + رسید + در صورت تمدید، renew با سرویس billing موجود (reuse؛ تاریخ از end_date).
- اگر gateway خاموش/بدون merchant: UI همان «هنوز آماده نیست» + درخواست تمدید desk بماند.

# داخل محدوده
- env فقط: PROVIDER / MERCHANT_ID / SANDBOX / CALLBACK_URL (نام‌ها با Settings پروژه هم‌خوان)
- adapter قابل تعویض؛ callback/verify فقط سرور؛ idempotent
- UI Ocean Dark در پنل ورزشکار (+ فلگ وضعیت در میز اگر لازم)
- pytest با mock درگاه؛ vitest/دود فرانت؛ بدون شبکهٔ واقعی در CI
- به‌روز کردن getting-started و .env.example خالی

# خارج از محدوده
- پیامک واقعی، ذخیره کارت، waitlist، چندشعبه
- دست زدن به منطق ورود یکپارچه مگر باگ blocker

# DoD
تست سبز، بدون secret در گیت، commit/push، گزارش OK/ناقص + نحوهٔ تست sandbox.
```
