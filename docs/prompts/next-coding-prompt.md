## هدف این برش (G / فاز ۱) — یک کار مشخص

صاحب باشگاه می‌خواهد وقتی در پنل مدیر/منشی طرح می‌سازد یا قیمت طرح را عوض می‌کند، بخش «عضویت / پلن‌ها» روی **صفحهٔ اول سایت** (لندینگ `frontend/index.html` سکشن `#plans`) همان داده‌ها را نشان دهد — نه قیمت‌های جعلی ثابت داخل HTML.

الان کارت‌های `#plans` سخت‌کد شده‌اند (مثلاً ماهانه ۱٬۲۰۰٬۰۰۰ تومان). API لیست طرح‌ها (`GET /api/v1/membership-plans`) فقط برای کارکنان desk است و لندینگ عمومی به آن وصل نیست.

نتیجهٔ مطلوب: بدون لاگین، لندینگ طرح‌های **فعال** را از API می‌گیرد و نام + قیمت تومان + خلاصه را نشان می‌دهد. عوض کردن قیمت در `#plans` پنل → بعد از رفرش لندینگ همان قیمت دیده شود.

## قوانین کسب‌وکار مرتبط (کوتاه — رعایت کن)

- قیمت روی طرح فعلی است؛ عوض کردنش سوابق membership/پرداخت گذشته را بازنویسی نمی‌کند (فقط نمایش قیمت فعلی طرح).
- طرح غیرفعال (`is_active=false`) در select تمدید و روی سایت عمومی نیاید — فقط فعال‌ها.
- مبالغ به **تومان**؛ UI فارسی RTL؛ اعداد ترجیحاً با جداکنندهٔ هزارگان فارسی/محلی مثل بقیهٔ فرانت.
- بدون کد ملی/عکس عضو؛ این برش دربارهٔ طرح است نه پروندهٔ عضو.
- سرور authz را enforce می‌کند: endpoint عمومی فقط خواندن طرح فعال؛ ساخت/ویرایش طرح همچنان فقط desk.

## داخل محدوده

### ۱) API عمومی فقط‌خواندنی

- یک endpoint عمومی شبیه الگوی trial، مثلاً:
  `GET /api/v1/public/membership-plans`
- بدون کوکی/لاگین.
- فقط طرح‌های `is_active=true`.
- پاسخ مینیمال برای سایت (مثلاً id، name، description، duration_days، session_count، base_price_toman، includes_locker). فیلدهای داخلی/حساس اضافه نکن.
- در صورت نیاز rate-limit سبک مثل دیگر endpointهای public (اگر در پروژه برای trial هست، الگوی مشابه؛ افراط نکن).
- endpoint موجود desk (`/membership-plans` با نقش) را خراب نکن؛ عمومی را جدا نگه دار تا اشتباهًا include_inactive به اینترنت باز نشود.

### ۲) لندینگ — رندر پویا

- در `frontend` (MPA فعلی، نه React): سکشن `#plans` / `.plan-grid` را از JS پر کن (مثلاً در `landing.js` یا ماژول کوچک جدا مثل `public-plans.js`).
- کارت‌های سخت‌کد قیمت را بردار یا به حالت خالی/اسکلت تبدیل کن که JS پر کند.
- برای هر طرح فعال: نام، قیمت تومان، چند بولت خلاصه از description و/یا مدت/جلسه/کمد (ساده و تمیز؛ بیش‌طراحی نکن).
- CTA کارت‌ها می‌تواند به `#trial` بماند (رزرو جلسه آزمایشی) — فروش آنلاین اجباری نیست.
- اگر API پایین بود: پیام کوتاه فارسی در همان سکشن (هم‌سبک بنر api-down موجود) و بدون قیمت جعلی گمراه‌کننده؛ یا اسکلت خالی + پیام «فعلاً از میز بپرسید».
- یک کارت را می‌توانی به‌عنوان featured علامت بزنی با قاعدهٔ سادهٔ ثابت در کد (مثلاً گران‌ترین فعال، یا وسط لیست اگر ۳ تا باشد) — **بدون** فیلد CMS جدید و بدون پنل طراحی.
- ظاهر را با CSS/کامپوننت‌های Ocean Dark موجود هماهنگ نگه دار؛ کارت تعاملی OK است چون همین الان الگوی plan روی لندینگ هست.

### ۳) تست

- Backend: تست happy path (لیست فعال‌ها بدون auth) + edge (طرح غیرفعال در پاسخ نیست؛ بدون auth 200 نه 401).
- Frontend vitest: رندر لیست از mock fetch + حالت خطای شبکه/API down.
- قبل از commit/push: `pytest` و در صورت لمس فرانت `npm test` سبز.

### ۴) docs

- یک اشارهٔ کوتاه در getting-started یا بخش لندینگ: قیمت سایت از طرح‌های فعال می‌آید؛ مدیریت از پنل `#plans`.
- seed را برای این برش اجباری عوض نکن مگر برای دموی واضح‌تر لازم باشد؛ اگر seed طرح فعال دارد همان کافی است.

## معیار پذیرش

1. با سرور API روشن: لندینگ `#plans` نام و قیمت طرح‌های فعال را از DB/API نشان می‌دهد.
2. در پنل desk قیمت یک طرح فعال را عوض کن → رفرش لندینگ همان قیمت جدید را نشان می‌دهد؛ عضویت/پرداخت قدیمی دست نخورده می‌ماند.
3. طرح غیرفعال روی لندینگ دیده نمی‌شود.
4. بدون لاگین، `GET .../public/membership-plans` کار می‌کند؛ invent کردن طرح از کلاینت ممکن نیست (فقط خواندن).
5. تست‌های مرتبط سبز؛ commit/push به origin/main طبق قانون Gym فقط با تست سبز.
6. به صاحب فارسی بگو: کاملاً OK یا ناقص؛ و بگو از کجا قیمت را عوض کند (`#plans` پنل).
