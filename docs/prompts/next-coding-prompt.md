# پرامپت مرحلهٔ بعد — برای چت سازنده (Agent)

آخرین به‌روزرسانی: ۱۴۰۴-۰۷-۲۵ (مدیر محصول — پس از تأیید حضور)  
مرحله: تمدید اشتراک + ثبت پرداخت + audit

کل بلاک زیر را کپی کن و در یک **چت Agent جدید** (سازنده، نه مدیر محصول) بفرست.

---

```text
# نقش
تو Agent سازندهٔ پروژهٔ GYM CONTROL هستی. مدیر محصول این مرحله را تأیید کرده.
docs را خودت پیدا و بخوان (از docs/README.md شروع کن).
منبع حقیقت: docs/product/business-rules.md بخش‌های طرح/عضویت و پول.
از auth، members، attendances موجود استفاده کن.
کار جدید فقط در frontend/ و backend/. پروتوتایپ HTML ریشه را تغییر نده.

# زبان با صاحب پروژه
فارسی، ساده، داخل <div dir="rtl">.
در پایان بگو کاملاً OK یا ناقص + نتیجهٔ تست.

# هدف این چت (فقط همین برش)
منشی/مدیر بتوانند برای عضو موجود اشتراک تمدید کنند، پرداخت ثبت کنند، برگشت بزنند، رسید ببینند/چاپ کنند، و این رویدادها در audit بمانند.

1) لیست طرح‌های فعال (برای انتخاب هنگام تمدید/ثبت عضویت)
2) تمدید: ایجاد ردیف membership جدید با مبلغ توافقی؛ شروع از پایان اشتراک مرجع (روز نسوزد)
3) ثبت پرداخت (ناقص مجاز) روی عضو/عضویت؛ روش cash/pos/transfer/online؛ online بدون درگاه (معمولاً paid همان لحظه؛ pending فقط اگر صریح بخواهی)
4) برگشت پرداخت (refund) — بدون ویرایش مبلغ ردیف قبلی
5) شمارهٔ رسید خودکار یکتا + در UI دکمهٔ چاپ (window.print ساده کافی است)
6) نوشتن audit_logs برای: تمدید/ایجاد عضویت، پرداخت، برگشت
7) حداقل UI React پشت لاگین (مثلاً از صفحهٔ عضو یا /billing)
8) تست‌های سبز برای قوانین پول و تمدید

# داخل محدوده
Backend (/api/v1) — نام‌ها می‌توانند کمی فرق کنند اگر واضح باشند:

طرح‌ها:
- GET /membership-plans  (فعال‌ها؛ manager+receptionist؛ trainer فقط خواندن اگر لازم UI — یا فقط staff desk)

عضویت:
- GET /members/{id}/memberships
- POST /members/{id}/memberships/renew  (یا /memberships)
  ورودی تقریبی: plan_id, agreed_amount_toman (>=0؛ صفر مجاز), optional base_membership_id برای تمدید از روی کدام اشتراک
  قانون تمدید: start_date = end_date اشتراک فعلی (یا روز بعد از end — یک سیاست را انتخاب و در docs یک خط بنویس؛ مهم: روز باقی‌مانده نسوزد، یعنی شروع از پایان فعلی نه از «امروز» اگر هنوز اعتبار دارد)
  قیمت پایهٔ طرح را روی سوابق گذشته بازنویسی نکن؛ فقط agreed روی ردیف جدید
- POST /memberships/{id}/cancel  اختیاری ولی مفید: قطع از امروز (status cancelled)؛ بدون برگشت خودکار پول

پرداخت:
- GET /members/{id}/payments
- POST /payments  body: member_id, membership_id?, amount_toman (>=0), method, status پیش‌فرض paid
- POST /payments/{id}/refund  فقط manager+receptionist؛ status → refunded؛ مبلغ ردیف را عوض نکن
- تولید receipt_number یکتا و ترتیبی/خوانا (مثلاً R-1001…)
- هیچ endpoint برای PATCH مبلغ پرداخت نباشد

بدهی (خواندنی):
- در جزئیات عضو یا پاسخ عضویت‌ها: debt_toman = جمع agreed باز − جمع پرداخت paid همان تعهدها (هم‌خوان با منطق حضور/seed)

Audit:
- جدول audit_logs موجود است؛ برای renew/payment/refund حداقل actor، action، entity، summary/payload بنویس

نقش‌ها:
- manager + receptionist: تمدید، پرداخت، برگشت
- trainer: این عملیات مالی ممنوع → ۴۰۳ (مگر فقط مشاهدهٔ شاگرد خودش اگر UI لازم داشت؛ پیش‌فرض مالی ندهد)
- بدون لاگین → ۴۰۱

قفل پرونده (اختیاری این برش):
- اگر ارزان است برای renew/payment یک قفل ساده ۵دقیقه‌ای بساز؛ وگرنه schema-todos را به‌روز بگذار و در گزارش بگو

Frontend:
- صفحه/جریان ساده پشت لاگین: انتخاب عضو → دیدن عضویت‌ها و بدهی → تمدید با طرح + مبلغ توافقی → ثبت پرداخت → برگشت → چاپ رسید
- روش online در لیست باشد با توضیح که به درگاه وصل نیست
- RTL/فارسی؛ تومان با جداکننده؛ تاریخ در UI شمسی اگر الگوی پروژه از قبل دارد — در غیر این صورت ISO موقتاً قابل قبول است اگر در گزارش بگویی
- گزارش مالی کامل مدیر / ثبت هزینه باشگاه در این برش لازم نیست

Docs:
- getting-started: چطور تمدید/پرداخت را امتحان کنند
- schema-todos: رسید/قفل را در صورت انجام به‌روز کن
- roadmap را فقط اگر مطمئنی تمام شد

# خارج از محدوده (نساز)
- درگاه آنلاین واقعی، پیامک
- لاگین ورزشکار / درخواست تمدید ورزشکار
- UI کامل گزارش سود/هزینه مدیر (مدل expense هست؛ برش جدا)
- کلاس، کمد، برنامه تمرینی
- تغییر HTML ریشه
- ویرایش amount پرداخت بعد از ثبت

# قوانین کسب‌وکار مرتبط (اجرا کن)
- قیمت طرح فعلی سوابق گذشته را عوض نکند؛ agreed روی همان عضویت
- صفر تومان توافقی مجاز؛ منفی ممنوع
- تمدید از پایان اشتراک فعلی (روز نسوزد)
- پرداخت ناقص مجاز؛ بدهی باقی می‌ماند
- درآمد ≠ بدهی؛ فقط paid در درآمد
- پرداخت ویرایش نشود؛ اصلاح = برگشت + پرداخت جدید
- online در enum باشد بدون اتصال درگاه
- برگشت با audit
- مخفی کردن UI امنیت نیست

# کیفیت
- pytest: تمدید تاریخ شروع درست، agreed منفی رد، پرداخت ناقص و محاسبه بدهی، refund بدون تغییر amount، ۴۰۱/۴۰۳، audit نوشته می‌شود، receipt یکتا
- vitest کوچک اگر منطقی است
- .env و دادهٔ واقعی در گیت نباشد
- بعد از تست سبز: commit + push به origin/main
- گزارش: endpointها، سیاست تاریخ تمدید، فرمت رسید، قفل پرونده آمده یا نه، چه چیز عمداً نساختی

# اگر مبهم شد
حدس نزن. business-rules را اجرا کن. جزئیات فرعی را ساده بگیر و مستند کن.
```
