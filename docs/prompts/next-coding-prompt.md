## هدف
صاحب می‌خواهد در کل محصول وب، هیچ گزینه‌ای برای **آرشیو / حذف / غیرفعال‌سازی اشخاص** نباشد:
- ورزشکار / عضو (`members`)
- کارکنان (منشی و …)
- مربی (همان حساب staff با نقش trainer)

یعنی منشی/مدیر دیگر نتوانند از UI (و ترجیحاً از API میز) کسی را آرشیو یا «حذف=غیرفعال» کنند.

## تصمیم محصول (صاحب — این برش)
- دکمه‌ها، متن‌های راهنما، و confirmهای مربوط به آرشیو عضو و غیرفعال/فعال‌سازی کارمند-مربی از پنل‌ها حذف شود.
- قانون قبلی «حذف دائمی ممنوع؛ فقط آرشیو/غیرفعال» برای اشخاص از مسیر میز برداشته می‌شود: در این نسخه **اصلاً از میز انجام نمی‌شود**.
- سوابق مالی و داده در DB می‌ماند؛ فقط راه UI/API میز برای خاموش کردن شخص بسته می‌شود.
- **خارج از این برش بماند:** غیرفعال‌سازی طرح عضویت، غیرفعال‌سازی کلاس گروهی، آزادسازی کمد، پایان واگذاری مربی↔عضو، حذف ردیف حرکت در برنامهٔ تمرینی (این‌ها شخص را حذف نمی‌کنند).

## داخل محدوده

### ۱) فرانت — اعضا
- `frontend/assets/js/members.js`: دکمه `data-archive` / متن آرشیو / handler مربوط را کامل بردار.
- اگر فیلتر `include_archived` یا UI مخصوص آرشیو فقط برای این جریان بوده و دیگر لازم نیست، ساده کن؛ لیست پیش‌فرض همچنان اعضای غیرآرشیو را نشان بدهد (اعضای آرشیو قدیمی seed/داده اگر هستند در لیست عادی نیایند — رفتار فعلی OK).
- تست‌های vitest که دکمه/جریان آرشیو را expect می‌کنند هم‌خوان کن یا حذف assert آرشیو.

### ۲) فرانت — کارکنان / مربی
- `frontend/assets/js/staff.js`: دکمه‌های `data-deactivate` و `data-activate`، hint «حذف = غیرفعال‌سازی…»، و handlerها را حذف کن. ویرایش نام/موبایل/نقش/رمز بماند.
- پنل منشی فقط مربی می‌سازد/ویرایش می‌کند — همان‌جا هم غیرفعال نباشد.
- `staff-plans.test.js` و هر تست UI مربوط را با نبودن این دکمه‌ها/hint به‌روز کن.

### ۳) بک‌اند — بستن مسیر میز
- `POST /api/v1/members/{id}/archive` → دیگر موفقیت‌آمیز نباشد: **۴۰۳ یا ۴۱۰** با پیام فارسی واضح مثل «آرشیو عضو از پنل در این نسخه فعال نیست.»
- `POST /api/v1/staff/{id}/deactivate` (و اگر فقط برای همین UI است `activate`) → همان سیاست: رد با پیام فارسی؛ یا activate را برای بازیابی اضطراری نگه ندار مگر لازم — ترجیح صاحب: گزینه‌های حذف/آرشیو/غیرفعال شخص از میز نباشد؛ **deactivate را حتماً ببند**. اگر `activate` را هم می‌بندی، یکدست کن و در گزارش بگو.
- اگر `PATCH /api/v1/staff/{id}` با `is_active: false` همان کار deactivate را می‌کند → این تغییر را هم رد کن (۴۰۰/۴۰۳)؛ ویرایش بقیهٔ فیلدها OK.
- مدل DB و ستون‌های `archived_at` / `is_active` را حذف migration نکن (داده و لاگین آرشیو قدیمی می‌تواند بماند).
- تست‌های pytest که archive/deactivate موفق را assert می‌کردند: انتظار را به ۴۰۳/۴۱۰ عوض کن؛ تست‌های «مربی نمی‌تواند آرشیو کند» را با سیاست جدید هم‌خوان کن.

### ۴) docs

- `docs/guides/getting-started.md` اگر چک‌لیست آرشیو/غیرفعال شخص دارد اصلاح کن.
