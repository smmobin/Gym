## هدف برش (J) — مدیر / منشی می‌تواند هم‌زمان مربی باشد

صاحب باشگاه تأیید کرد: در خیلی از باشگاه‌ها مدیر خودش مربی است؛ گاهی منشی هم مربی می‌شود. این باید روی **یک موبایل / یک ردیف `users`** پشتیبانی شود — نه با ساخت حساب دوم (موبایل کارکنان یکتاست).

قوانین کسب‌وکار مرتبط (خلاصهٔ الزام‌آور از business-rules):
- مربی بودن = کارمند قابل‌واگذاری به شاگرد + پنل `/trainer/`؛ الزامی به عضو/ورزشکار بودن نیست.
- مجاز: **مدیر+مربی** و **منشی+مربی** روی یک حساب.
- غیرمجاز در v1: **مدیر+منشی** روی یک حساب.
- همان موبایل همچنان می‌تواند ردیف ورزشکار (`members`) جدا داشته باشد.
- ورود: چند هویت/نقش قابل‌ورود → UI «با کدام نقش وارد می‌شوید؟»؛ هیچ اولویت خودکاری نیست.
- وقتی نقش **مدیر یا منشی** انتخاب شد → فقط رمز. وقتی نقش **مربی** انتخاب شد → OTP (+رمز پشتیبان) مثل مربی خالص.
- سشن کارکنان باید نقش فعال ورود (`acting_role` یا معادل) را نگه دارد؛ سرور همان را برای پنل و `require_roles` enforce کند. کلاینت بعد از ورود میز نتواند خود را مربی جا بزند یا برعکس.
- با نقش مربی: فقط شاگردهای خودش (مثل مربی خالص). با نقش میز: دسترسی همان نقش میز؛ مسیرهایی که از قبل برای مدیر روی برنامه مجاز بود سر جایش بماند.
- در UI کارکنان: برای مدیر/منشی گزینهٔ واضح «مربی هم هست». وقتی فعال است در فهرست مربیان، واگذاری شاگرد، و `trainer_user_id` کلاس‌ها دیده/قابل‌استفاده باشد.
- غیرفعال کردن حساب → هر دو مسیر میز و مربی قطع می‌شود.

## مدل داده (پیشنهاد الزامی مگر دلیل قوی برای طرح بهتر)

- روی `users` فیلد بولین مثلاً `also_trainer` (پیش‌فرض false).
- وقتی `role == trainer`: همان مربی خالص؛ `also_trainer` بی‌معنی/نادیده (یا false اجباری).
- وقتی `role` برابر manager یا receptionist و `also_trainer == true`: دو هویت staff برای lookup بساز (یکی با role میز، یکی با role=trainer).
- موبایل یکتا بماند — دو ردیف users برای یک نفر نساز.
- migration Alembic + به‌روزرسانی seed (حداقل یک مثال واقعی: مثلاً مدیر seed با `also_trainer=true` و حداقل یک شاگرد وصل‌شده تا صاحب در `/trainer/` ببیند؛ یا منشی نمونه — یکی کافی است؛ PII واقعی نگذار).
- در staff create/update API و UI (`#staff` مدیر و منشی): چک‌باکس/سوییچ «مربی هم هست» فقط وقتی نقش میز manager یا receptionist است. منشی طبق قواعد فعلی فقط مربی می‌سازد/ویرایش می‌کند — اگر منشی کاربر میز دیگری را ویرایش می‌کند و مجاز است، همان فلگ را برای منشی‌ها فقط اگر از قبل در محدودهٔ دسترسی‌اش است رعایت کن؛ مدیر روی همه.
- تغییر نقش از trainer خالص به receptionist/manager یا برعکس را بی‌جهت بزرگ نکن؛ تمرکز روی فلگ `also_trainer` برای میز است.

## ورود و سشن

- `list_identities_for_mobile` / lookup را گسترش بده: یک user با also_trainer می‌تواند **دو** LoginIdentity از نوع staff برگرداند (مثلاً manager + trainer)، به‌علاوه athlete اگر عضو باشد.
- `resolve_identity` باید با `kind`+`role` دقیقاً یکی را انتخاب کند؛ اگر چند staff identity هست و role نیامده → 409 مثل چندهویتی.
- `staff_sessions` (یا معادل): ستون `acting_role` (یا نام هم‌معنی) هنگام create_session از هویت انتخاب‌شده پر شود.
- `get_current_user` / `require_roles`: مجوز را بر اساس **acting_role سشن** بده نه فقط `users.role` خام. مثال: مدیر با also_trainer که با acting_role=trainer وارد شده به گزارش مالی مدیر و staff admin → ۴۰۳؛ به `/trainer/` و API شاگردان خودش → مجاز.
- پاسخ login/me باید role مؤثر (acting) را برگرداند تا فرانت به پنل درست redirect کند.
- فرانت `/login/`: chooser وقتی ۲+ هویت (شامل دو نقش staff)؛ بعد از انتخاب، همان مسیر auth نقش (رمز میز / OTP مربی).
- اگر کاربر فقط میز بدون also_trainer است → یک هویت staff (مثل امروز).
- اگر فقط trainer خالص است → یک هویت trainer.

## مربیان / کلاس / برنامه

- `list_trainers` و هر جایی که `User.role == trainer` فیلتر می‌شود: شامل `also_trainer == true` (و is_active) هم بشود.
- واگذاری شاگرد، لیست شاگردان مربی، نوشتن برنامه وقتی acting_role=trainer یا role=trainer: همان قواعد «فقط شاگردهای خودش».
- ساخت/ویرایش کلاس با trainer_user_id: اجازه بده id مدیری/منشی‌ای که also_trainer دارد هم انتخاب شود (ولیدیشن سرور).
- هشدار تداخل ساعت همان مربی برای این idها هم کار کند.

## UI

- Ocean Dark MPA، RTL، تم dark/light موجود را نشکن.
- فرم کارکنان: سوییچ واضح فارسی «مربی هم هست» با توضیح کوتاه یک خطی.
- بعد از ورود با نقش مربی → `/trainer/`؛ با مدیر → `/manager/`؛ با منشی → `/receptionist/`.
- جابه‌جایی داخل سشن بین پنل میز و مربی بدون logout مجدد در این برش اجباری نیست (خارج محدودهٔ نرم)؛ اگر لینک ساده «خروج و ورود با نقش دیگر» خواستی اختیاری است ولی اولویت با درست بودن chooser ورود و acting_role است.

## امنیت

- هرگز به کلاینت اعتماد نکن برای ارتقای نقش؛ acting_role فقط از سشن سرور.
- نمی‌شود با cookie میز به APIهای مخصوص trainer بدون acting_role=trainer رسید (و برعکس برای عملیات حساس مدیر).
- Rate limit / پیام خطای عمومی ورود مثل برش I حفظ شود.

## تست

Backend (pytest):
- manager با also_trainer → lookup حداقل ۲ هویت staff (مدیر + مربی)؛ + athlete اگر seed کردی.
- ورود با role=manager → فقط password؛ session acting_role=manager؛ دسترسی میز OK؛ مسیر فقط-مربی محدود شود.
- ورود با role=trainer روی همان user → OTP (123456 در dev بدون SMS) یا password پشتیبان؛ acting_role=trainer؛ پنل/API مربی فقط شاگردهایش؛ گزارش مالی → ۴۰۳.
- receptionist+also_trainer مشابه در حد یک تست کلیدی.
- list_trainers شامل also_trainer؛ assign مربی به چنین کاربری OK.
- کاربر بدون also_trainer رفتار قبلی را بشکند.

Frontend (vitest):
- chooser وقتی دو نقش staff برمی‌گردد.
- نمایش کنترل «مربی هم هست» در فرم staff (در حد منطقی).

قبل از commit/push: `pytest` و تست فرانت مربوط سبز.

## معیار پذیرش

1. می‌توان روی یک مدیر (یا منشی) «مربی هم هست» زد بدون موبایل دوم.
2. همان نفر در فهرست مربیان و واگذاری شاگرد ظاهر می‌شود.
3. ورود با موبایل → انتخاب «مدیر» یا «مربی» (و در صورت وجود ورزشکار)؛ روش auth درست است.
4. مجوزها بر اساس نقش ورود (acting_role) روی سرور درست است.
5. تست سبز + commit/push به origin/main طبق قانون Gym؛ گزارش فارسی OK/ناقص به صاحب.
