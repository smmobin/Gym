## هدف این برش (F) — یک کار مشخص

الان `python -m app.db.seed` و خیلی از تست‌های pytest با فراخوانی `seed()` اول **همهٔ جدول‌های دامنه را خالی می‌کنند** (`clear_domain_data`) بعد دادهٔ ساختگی می‌ریزند. چون pytest همان `DATABASE_URL` فایل `.env` (دیتابیس کار روزمرهٔ صاحب) را می‌زند، اجرای تست یا seed دوباره، **دادهٔ واقعی/دستی صاحب را پاک می‌کند**.

صاحب می‌خواهد:

1) دادهٔ تست/نمونه اگر لازم است **اضافه** شود به دادهٔ موجود — نه اینکه اول همه چیز پاک شود.
2) اگر همان ردیف نمونه از قبل هست (مثلاً موبایل seed)، دوباره ساخته نشود و دادهٔ دیگر پاک نشود.
3) پاک‌کردن عمدی همهٔ داده فقط با دستور جدا `python -m app.db.wipe_dev_data` بماند (همان قابلیتی که قبلاً خواسته شده).
4) اجرای `pytest` هرگز نباید دیتابیس کار روزمرهٔ صاحب را خالی یا خراب کند.

## داخل محدوده

### الف) جدا کردن دیتابیس تست از دیتابیس کار (اجباری)

- تست‌های backend باید به یک Postgres **جدا** وصل شوند (مثلاً نام پیشنهادی `gym_control_test`)، نه به DB روزمرهٔ `gym_control` داخل `.env`.
- در `backend/tests/conftest.py` (یا معادل تمیز): قبل از import اپ / ساخت engine، `DATABASE_URL` تست را ست کن؛ یا از env مثل `TEST_DATABASE_URL` بخوان با پیش‌فرض امن به DB تست جدا.
- اگر DB تست وجود نداشت: در docs/getting-started یا testing بگو یک‌بار ساخته شود (`CREATE DATABASE gym_control_test`) و migration روی همان زده شود — دستور واضح PowerShell/SQL برای ویندوز.
- روی DB تست، تست‌ها می‌توانند برای ایزوله بودن wipe+seed یا تراکنش/rollback داشته باشند — چون آن DB مال کار روزمره نیست.
- **هرگز** در مسیر pytest پیش‌فرض به همان URL روزمرهٔ صاحب wipe نزن.

### ب) seed افزایشی / idempotent (بدون پاک‌سازی پیش‌فرض)

- `seed()` دیگر به‌صورت پیش‌فرض `clear_domain_data` / `_clear_domain` را صدا نزند.
- رفتار درست: برای هر موجودیت seed با کلید پایدار (موبایل کارکنان/اعضا، کد طرح، شماره کمد، و مشابه) اگر از قبل هست → همان را بگیر / در صورت نیاز فیلدهای غیرمخرب seed را هم‌تراز کن؛ اگر نیست → بساز.
- دادهٔ غیر-seed موجود در DB (مدیر واقعی، اعضایی که صاحب ساخته، پرداخت‌ها، …) **دست نخورند و پاک نشوند**.
- اگر دو ردیف seed با هم conflict منطقی دارند، با upsert روی کلید یکتا حل کن؛ wipe نکن.
- CLI `python -m app.db.seed` همان رفتار افزایشی را داشته باشد.
- گارد production فعلی بماند: در production-like بدون `ALLOW_DESTRUCTIVE_SEED` نباید seed مخرب اجرا شود. چون seed دیگر wipe نمی‌کند، پیام/گارد را طوری به‌روز کن که معنی‌دار باشد (مثلاً seed افزایشی در prod همچنان ممنوع یا فقط با فلگ صریح — طبق security و deploy؛ پیش‌فرض: روی production-like همچنان refuse مگر فلگ صریح؛ روی development آزاد و غیرمخرب).

### ج) wipe فقط عمدی

- `clear_domain_data` و `python -m app.db.wipe_dev_data` سر جایشان بمانند برای «عمداً همه را خالی کن».
- از داخل `seed()` دیگر wipe صدا زده نشود.
- اگر جایی برای تست نیاز به DB تمیز است: فقط روی DB تست، صریحاً wipe یا fixture ایزوله — نه روی DB روزمره.

### د) هم‌خوان کردن تست‌های موجود

- هر تستی که امروز با `seed()` فرض می‌کند «دنیای خالی فقط با seed» دارد را طوری اصلاح کن که:
  - یا روی DB تست اول wipe/seed کنترل‌شده بزند،
  - یا fixture ماژولی/سراسری روی DB تست state شناخته‌شده بسازد،
  - بدون تکیه به پاک کردن DB صاحب.
- تست‌های گارد wipe/seed را نگه دار و در صورت تغییر رفتار seed، تست جدید برای «seed دادهٔ غیر-seed را پاک نمی‌کند» اضافه کن (happy path + یک edge: ردیف seed تکراری دوباره duplicate نمی‌سازد).
- frontend vitest اگر به DB وصل نیست دست نزن مگر لازم.

### ه) مستندات

- `docs/guides/getting-started.md` و `docs/guides/testing.md`: توضیح ساده که
  - seed = اضافه/به‌روز نمونه بدون پاک کردن بقیه
  - wipe = فقط وقتی عمداً می‌خواهی همه خالی شود
  - pytest = DB جدا (`gym_control_test` / `TEST_DATABASE_URL`)
- در صورت نیاز یک خط در `roadmap-status` لازم نیست از سازنده؛ مدیر محصول بعداً می‌نویسد. ولی getting-started/testing را حتماً درست کن.

## خارج محدوده

- دیپلوی production واقعی، لیارا، تغییر درگاه/پیامک
- OTP، UI ساخت مدیر، برگرداندن حساب دمو به UI
- تغییر قوانین کسب‌وکار پول/عضویت مگر برای کلید یکتای seed لازم باشد
- دست زدن به HTML ریشهٔ پروتوتایپ / GitHub Pages مگر ضروری نباشد (کار جدید فقط `frontend/` + `backend/` + docs راهنما)
- بازنویسی کل سوئیت تست از صفر اگر با اصلاح fixture/conftest حل می‌شود

## قوانین مرتبط (کوتاه)

- دادهٔ واقعی عضو در seed/گیت نرود؛ seed فقط ساختگی.
- سرور امنیت را enforce می‌کند؛ بدون secret در گیت؛ `.env` commit نشود.
- پول/عضویت گذشته با seed دستکاری مخرب نشود (seed فقط ردیف‌های نمونهٔ خودش را می‌سازد/به‌روز می‌کند).
- DoD: تست سبز قبل از commit/push.

## معیار پذیرش

1. روی یک DB که از قبل عضو/مدیر دستی دارد: اجرای `python -m app.db.seed` آن ردیف‌ها را پاک نمی‌کند؛ فقط نمونهٔ seed را در صورت نبود اضافه می‌کند.
2. اجرای `pytest` در backend به DB تست جدا می‌رود و DB روزمرهٔ `.env` را wipe نمی‌کند.
3. `python -m app.db.wipe_dev_data` همچنان همهٔ دامنه را خالی می‌کند (با گارد prod).
4. تست‌های مرتبط سبز؛ حداقل یک تست صریح برای «seed دادهٔ موجود غیر-seed را حذف نمی‌کند».
5. docs راهنما به‌روز.

## بعد از اتمام

- تست backend (و frontend اگر لمس شد) را اجرا کن؛ فقط با سبز commit و push به origin/main طبق قانون Gym.
- به صاحب فارسی و شفاف بگو: کاملاً OK یا ناقص؛ چطور DB تست بسازد؛ seed دیگر پاک نمی‌کند؛ wipe کی استفاده شود.
