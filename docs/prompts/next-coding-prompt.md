## هدف برش (I) — ورود جدید

صاحب می‌خواهد جریان ورود یکپارچه عوض شود. قوانین فعلی «موبایل+رمز برای همه» و «OTP ورود در v1 نیست» را این برش **عمداً جایگزین** می‌کند؛ بعد از پیاده‌سازی `business-rules.md` بخش ورود و پیامک را با رفتار جدید هم‌خوان کن.

### جریان مطلوب UI (`/login/`)

1) **قدم ۱ — فقط موبایل:** یک باکس موبایل واضح‌تر/کمی بزرگ‌تر از الان؛ بدون فیلد رمز در همین قدم. فونت/تم Ocean حفظ شود.
2) کاربر «ادامه» می‌زند → API سرور موبایل را resolve می‌کند (کلاینت نقش را حدس نمی‌زند).
3) **اگر چند هویت روی یک موبایل** (مثلاً همان شماره هم `users` کارکنان است هم `members` ورزشکار با امکان ورود): **صفحه/گام انتخاب نقش** نشان بده: «با کدام نقش وارد می‌شوید؟» با گزینه‌های واقعی موجود (مثلاً منشی / مربی / ورزشکار). **دیگر اولویت خودکار کارکنان بر ورزشکار اعمال نشود** وقتی هر دو موجودند — انتخاب با کاربر است. پیش‌فرض اجباری روی یک نقش نگذار مگر فقط یک گزینه باشد.
4) بعد از دانستن نقش مقصد (یا وقتی فقط یک هویت بود):
   - **مدیر یا منشی** → فقط **رمز عبور** (الزامی). بدون OTP.
   - **مربی یا ورزشکار** → مسیر اصلی **کد پیامک (OTP)**؛ کنارش کنترل شیک «ورود با رمز عبور» که با **انیمیشن نرم** بین فرم OTP و فرم رمز جابه‌جا شود (جذاب، accessible، RTL).
5) ورود موفق → redirect به پنل همان نقش مثل امروز (`/manager/`، `/receptionist/`، `/trainer/`، `/athlete/`).

### پیامک / حالت توسعه

- مسیر API ارسال و تأیید OTP را کامل بساز (حتی اگر SMS واقعی خاموش است).
- وقتی SMS واقعی از env فعال نیست (development / `SMS_PROVIDER=none`): کد OTP ثابت **`123456`** برای تأیید ورود مربی/ورزشکار قبول شود تا صاحب بدون پنل پیامک بتواند تست کند. در UI می‌توانی راهنمای کوتاه توسعه نشان بدهی که فقط در غیر-production دیده شود.
- در **production-like** بدون SMS واقعی: ارسال OTP واقعی نکن و کد ثابت را **قبول نکن**؛ پیام واضح «پیامک هنوز آماده نیست» + پیشنهاد ورود با رمز اگر رمز ست شده.
- وقتی SMS واقعی فعال است: OTP تصادفی کوتاه‌عمر، ذخیره هش‌شده سمت سرور، انقضا، سقف تلاش، rate-limit روی send/verify. موبایل فقط از DB خوانده شود.

### رمز عبور

- مدیر/منشی: مثل قبل password_hash روی `users`.
- مربی: password روی `users` برای مسیر پشتیبان «ورود با رمز» بماند؛ میز/مدیر همچنان می‌تواند رمز را عوض کند.
- ورزشکار: `members.password_hash` برای مسیر پشتیبان بماند؛ میز می‌تواند ست کند. مسیر اصلی OTP است؛ اگر رمز ست نشده و کاربر «ورود با رمز» زد → پیام واضح که رمز ست نشده / به میز مراجعه کند.
- حداقل طول رمز مثل قوانین فعلی (۸+) جایی که رمز وارد می‌شود.

### تداخل موبایل — جزئیات سرور

- Lookup نباید فقط «اول staff» لاگین کند.
- پاسخ lookup تقریباً چنین مفهومی (نام فیلدها آزاد، معنی ثابت):
  - لیست هویت‌های فعال برای آن موبایل: مثلاً `{ kind: "staff"|"athlete", role?: "manager"|"receptionist"|"trainer" }`
  - اگر ۰ → خطای عمومی «اطلاعات نادرست» / موبایل ثبت‌نشده (بدون افشای زیاد).
  - اگر ۱ → مستقیم همان مسیر auth برای همان نقش.
  - اگر ۲+ → کلاینت UI انتخاب نقش را نشان دهد؛ سپس auth با `role`/`kind` انتخاب‌شده + روش مربوط.
- بعد از انتخاب نقش، session همان نوع قبلی بماند (cookie staff در برابر athlete جدا مثل معماری فعلی).

### UI / UX

- انیمیشن بین قدم‌ها و بین OTP↔رمز: نرم، شیک، بدون شلوغی؛ `prefers-reduced-motion` را احترام بگذار.
- بدون radio نقش روی قدم ۱؛ انتخاب نقش فقط وقتی تداخل واقعی است.
- RTL/فارسی/تم dark-light موجود را نشکن.
- صفحهٔ لاگین ورزشکار جدا (`athlete/login`) را یا به همین جریان یکپارچه هدایت کن یا هم‌رفتار کن — یک منبع حقیقت ورود عمومی ترجیح دارد (`/login/`).

### امنیت

- Rate limit روی lookup / login password / otp send / otp verify.
- OTP را در لاگ یا پاسخ API برنگردان (جز حالت dev که UI ممکن است راهنما نشان دهد؛ کد را در JSON موفقیت send برنگردان مگر فقط در APP_ENV=development و صریح برای تست — ترجیح: حتی در dev در response نباشد و فقط ثابت 123456 سمت سرور verify شود).
- سرور مسیر و نقش را enforce کند؛ کلاینت نتواند با نقش اشتباه session بگیرد.

### تست

- Backend: lookup تک‌هویت؛ تداخل staff+athlete → چند گزینه؛ مدیر/منشی فقط password؛ مربی/ورزشکار OTP با 123456 در حالت بدون SMS؛ سوئیچ password برای مربی/ورزشکار؛ رد OTP غلط؛ production-like بدون SMS ثابت را رد کند.
- Frontend vitest: رندر قدم موبایل؛ نمایش chooser هنگام چند هویت؛ انیمیشن/سوییچ OTP↔رمز در حد تست منطقی (نه screenshot).
- قبل از commit/push: pytest + npm test سبز.

### docs

- `business-rules.md`: بخش ورود یکپارچه و خط «OTP در v1 نیست» را با رفتار جدید عوض کن (مدیر/منشی رمز؛ مربی/ورزشکار OTP+رمز پشتیبان؛ تداخل موبایل → انتخاب نقش توسط کاربر).
- getting-started: یک پاراگراف کوتاه دربارهٔ تست OTP با 123456 در dev.
- roadmap را سازنده عوض نکند مگر لازم؛ مدیر محصول بعداً تأیید می‌کند.

## خارج محدوده

- فراموشی رمز مدیر/منشی با SMS
- UI ساخت مدیر
- PWA، وردپرس، فاز آپلود لوگوی پنل
- اتصال اجباری کاوه‌نگار در این برش اگر env نیست (adapter موجود را reuse کن وقتی enabled)
- تغییر قوانین پول/عضویت غیرمرتبط

## معیار پذیرش

1. `/login/` اول فقط موبایل (بزرگ‌تر/واضح).
2. مدیر و منشی بعد از موبایل (و در صورت نیاز انتخاب نقش) فقط با رمز وارد می‌شوند.
3. مربی و ورزشکار پیش‌فرض OTP؛ در dev بدون SMS کد 123456 کار می‌کند؛ گزینه ورود با رمز با انیمیشن شیک موجود است.
4. موبایل مشترک کارکنان+ورزشکار → صفحه انتخاب نقش؛ دیگر staff به‌اجبار اول نیست.
5. تست سبز + commit/push به origin/main طبق قانون Gym؛ گزارش فارسی OK/ناقص به صاحب.
