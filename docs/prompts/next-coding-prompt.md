# پرامپت مرحلهٔ بعد — برای چت سازنده (Agent)

آخرین به‌روزرسانی: ۱۴۰۴-۰۷-۲۵ (مدیر محصول — پس از تأیید برش اعضا)  
مرحله: حضور ورود/خروج (API محافظت‌شده + حداقل UI)

کل بلاک زیر را کپی کن و در یک **چت Agent جدید** (سازنده، نه مدیر محصول) بفرست.

---

```text
# نقش
تو Agent سازندهٔ پروژهٔ GYM CONTROL هستی. مدیر محصول این مرحله را تأیید کرده.
docs را خودت پیدا و بخوان (از docs/README.md شروع کن).
منبع حقیقت رفتار: docs/product/business-rules.md بخش حضور و غیاب (+ پول فقط برای هشدار بدهی).
از auth و members موجود استفاده کن؛ چرخ را دوباره نساز.
کار جدید فقط در frontend/ و backend/. پروتوتایپ HTML ریشه را تغییر نده.

# زبان با صاحب پروژه
فارسی، ساده، داخل <div dir="rtl">. اصطلاح فنی را یک جمله توضیح بده.
در پایان بگو کاملاً OK یا ناقص + نتیجهٔ تست.

# هدف این چت (فقط همین برش)
منشی/مدیر (و مربی برای شاگرد خودش) بتوانند برای عضو موجود ورود و خروج ثبت کنند، با قوانین کسب‌وکار.

1) API ثبت ورود (check-in) با نوع: gym / class / pt
2) API ثبت خروج (check-out) برای حضور باز
3) API لیست حضور امروز (یا حضورهای باز + امروز) برای صفحهٔ عملیاتی
4) حداقل UI React پشت لاگین: انتخاب/جستجوی عضو + ورود با نوع + خروج + نمایش هشدارها
5) تست خودکار سبز برای قوانین کلیدی زیر

# داخل محدوده
Backend (پیشوند /api/v1) — نام‌ها می‌توانند کمی فرق کنند اگر واضح باشند:
- POST /attendances/check-in
  body تقریبی: member_id, attendance_type (gym|class|pt), confirm_second_visit?: bool
- POST /attendances/{id}/check-out   (یا معادل با member_id اگر فقط یک حضور باز مجاز است)
- GET  /attendances?date=today یا /attendances/today (+ فیلتر عضو اختیاری)

منطق اجباری (business-rules):
- ورود و خروج هر دو معنا دارند؛ حضور باز = check_out_at خالی
- اشتراک منقضی / بدون اشتراک معتبر فعال → ورود ممنوع (۴۰۹ یا ۴۲۲ واضح)
- اشتراک معتبر + بدهی → ورود مجاز؛ پاسخ باید هشدار بدهی داشته باشد (مثلاً warning flag/message)
- ورود دوم در همان روز تقویمی (با توجه به timezone باشگاه؛ اگر ساده است از Asia/Tehran یا تاریخ محلی سرور با توضیح در docs): بدون confirm_second_visit → خطا/نیاز به تأیید؛ با تأیید منشی → مجاز
- نوع حضور را منشی انتخاب می‌کند: gym / class / pt
- طرح جلسه‌ای: وقتی ورود موفق به بستهٔ جلسه‌ای مرتبط بخورد، sessions_remaining یک واحد کم شود (کمتر از صفر نشود؛ اگر جلسه نمانده → ورود ممنوع مگر سیاست واضح دیگری در docs — پیش‌فرض: ممنوع)
- برای نوع pt از بسته/عضویت مرتبط با جلسه مربی استفاده کن؛ gym از بسته سالن/عمومی — اگر چند عضویت فعال است، قانون انتخاب را ساده و مستند کن (مثلاً صریح membership_id اختیاری در body، وگرنه بهترین تطبیق)
- مربی: فقط برای شاگرد خودش (assignment فعال) می‌تواند ورود/خروج بزند؛ بقیه → ۴۰۳. ثبت برای دیگران فقط manager/receptionist
- عضو آرشیو شده → ورود ممنوع
- recorded_by_user_id = کاربر فعلی

خروج خودکار پایان روز:
- حداقل: وقتی می‌خواهی ورود جدید بزنی یا لیست امروز را می‌گیری، اگر حضور باز مربوط به روز قبل (یا بعد از day_end_time تنظیمات) مانده، خودکار check_out بزن و در پاسخ/لاگ مشخص کن
- کرون جدا اجباری نیست؛ اگر فقط همین مسیر را ساختی در گزارش بگو و schema-todos را به‌روز کن

بدهی:
- از همان منطق توافقی − پرداخت‌های paid استفاده کن (اگر helper بدهی از قبل هستreuse کن؛ از seed/test_seed_debt الگو بگیر)

نقش‌ها:
- manager, receptionist: کامل
- trainer: فقط شاگردهای خودش
- بدون لاگین → ۴۰۱

Frontend:
- صفحهٔ ساده پشت لاگین (مثلاً /attendance)
- جستجو/انتخاب عضو (می‌توانی از API members موجود استفاده کنی)
- دکمه ورود + انتخاب نوع + نمایش هشدار بدهی / تأیید ورود دوم
- دکمه خروج برای حضور باز
- RTL/فارسی؛ بدون داشبورد شلوغ و بدون پرداخت/تمدید در این برش

Docs:
- getting-started: یک پاراگراف چطور حضور را امتحان کنند
- schema-todos: وضعیت خروج خودکار را به‌روز کن
- roadmap را فقط اگر مطمئنی تمام شد عوض کن؛ وگرنه مدیر محصول

# قوانین کسب‌وکار مرتبط (خلاصه — اجرا کن)
- ورود و خروج هر دو لازم
- منقضی → ورود ممنوع؛ بدهی با اشتراک معتبر → ورود + هشدار
- ورود دوم همان روز → هشدار + تأیید منشی
- نوع: سالن / کلاس / جلسه مربی
- مربی فقط شاگرد خودش
- جلسهٔ مربی مصرف جدا از سالن
- مخفی کردن UI امنیت نیست

# کیفیت

# اگر مبهم شد
حدس نزن. business-rules را اجرا کن. انتخاب‌های فرعی را ساده بگیر، در docs یک خط بنویس، در گزارش بگو.
```
