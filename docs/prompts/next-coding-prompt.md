# پرامپت مرحلهٔ بعد — برای چت سازنده (Agent)

آخرین به‌روزرسانی: ۱۴۰۴-۰۷-۲۷ (مدیر محصول — پس از تأیید freeze)  
مرحلهٔ کدنویسی اختیاری بعدی: **رزرو کلاس گروهی توسط ورزشکار**

اگر صاحب هنوز دیپلوی نکرده: اول کار دستی طبق `docs/guides/deploy.md` و `backup.md`؛ این برش اختیاری است.

متن زیر را **کامل کپی** کن و در چت Agent سازنده بفرست.

---

```text
# نقش
تو Agent سازندهٔ GYM CONTROL هستی (نه مدیر محصول).
docs را خودت از docs/README.md و اسناد مرتبط پیدا کن و بخوان.
منبع حقیقت رفتار: docs/product/business-rules.md (بخش کلاس گروهی + نقش ورزشکار) و الگوی فعلی پنل ورزشکار و رزرو کارکنان.
کار جدید فقط در frontend/ و backend/. HTML ریشه / GitHub Pages را دست نزن مگر صریحاً لازم باشد (اینجا لازم نیست).

# زمینهٔ فعلی (فرض نکن — در کد تأیید کن)
- کارکنان از قبل کلاس گروهی می‌سازند و رزرو می‌کنند: /classes و API زیر /api/v1/group-classes/... با ظرفیت سروری (بدون overbook / waitlist).
- ورزشکار لاگین جدا دارد (کوکی gym_athlete_session)، پنل /athlete با عضویت/پرداخت/برنامه/اعلان/درخواست تمدید — ولی هنوز لیست کلاس و رزرو خودش را ندارد.
- freeze عضویت انجام شده؛ این برش به freeze کاری ندارد.

# هدف این برش (یک vertical slice)
ورزشکار لاگین‌شده بتواند:
1) کلاس‌های گروهی فعال/آینده را ببیند (ظرفیت باقی‌مانده، عنوان، زمان، مربی در صورت وجود).
2) خودش را برای یک کلاس رزرو کند (فقط member_id خودش).
3) رزرو فعال خودش را لغو کند.
ظرفیت و قوانین پر بودن کلاس باید همان منطق سروری موجود کارکنان باشد (reuse سرویس capacity؛ دوباره‌نویسی قوانین ممنوع).

# داخل محدوده
Backend:
- endpointهای ورزشکار زیر پیشوند /api/v1/athlete/... با Depends(get_current_athlete):
  - GET لیست کلاس‌های قابل‌نمایش برای ورزشکار (فقط فعال؛ ترجیحاً starts_at در آینده یا «امروز به بعد» طبق الگوی seed/UI موجود — تصمیم را در تست و docs کوتاه ثبت کن).
  - GET رزروهای خود ورزشکار (یا جاسازی در پاسخ لیست کلاس با فلگ «من رزرو دارم»).
  - POST رزرو برای class_id مشخص → فقط برای member لاگین‌شده؛ member_id از کلاینت قبول نکن / نادیده بگیر.
  - POST لغو رزرو خود (با booking_id یا class_id — یک قرارداد واضح و تست‌شده).
- Authz سخت سروری: ورزشکار هرگز رزرو عضو دیگر، no-show، attended، ایجاد/ویرایش کلاس، یا لیست همهٔ رزروهای کلاس را نگیرد.
- نقش کارکنان برای /group-classes دست‌نخورده بماند.
- خطاهای فارسی واضح برای: پر بودن ظرفیت (409)، رزرو تکراری، کلاس غیرفعال، رزرو مال دیگری، بدون سشن ورزشکار (401).
- در صورت نیاز migration فقط اگر فیلد جدیدی واقعاً لازم است؛ ترجیح با جداول فعلی ClassBooking / GroupClass.
- seed: حداقل یک کلاس آینده با ظرفیت خالی و یک سناریو که ورزشکار seed (مثلاً علی 09121111001 / رمز dev) بتواند رزرو کند؛ PII واقعی ممنوع.

Frontend:
- در پنل /athlete (AthleteHomePage یا بخش/مسیر واضح هم‌سبک UI موجود): لیست کلاس‌ها + دکمه رزرو/لغو + نمایش ظرفیت باقی‌مانده و وضعیت «رزرو شده توسط من».
- کوکی/api همان الگوی فعلی athlete؛ RTL فارسی؛ تاریخ/زمان مطابق الگوی پروژه (جلالی در UI اگر بقیهٔ athlete همین‌طور است).
- تست vitest برای happy path رزرو/لغو و حداقل یک شکست (مثلاً پر بودن یا 401).

Tests:
- pytest برای athlete book/cancel + capacity full + cannot book for someone else + staff endpoints still work.
- vitest برای UI ورزشکار.
- قبل از commit همهٔ تست‌های مرتبط سبز.

# خارج از محدوده (صریح — نساز)
- پیامک واقعی، درگاه پرداخت، تمدید خودکار بعد از پرداخت.
- لیست انتظار، overbook، رزرو بر اساس جنسیت.
- تغییر HTML پروتوتایپ ریشه.
- دیپلوی با credential صاحب، تغییر production secrets.
- no-show / attended از سمت ورزشکار.
- بازنویسی کل پنل کارکنان /classes.
- فروشگاه کالا، چندشعبه.

# قوانین کسب‌وکار مرتبط (خلاصه — جزئیات در business-rules)
- ظرفیت دارد؛ پر شد → رزرو بیشتر ممنوع (بدون overbook / waitlist در v1).
- قبلاً رزرو نسخهٔ اول فقط منشی/مدیر بود؛ حالا ورزشکار فقط برای خودش اضافه می‌شود؛ میز همچنان می‌تواند برای اعضا رزرو کند.
- لغو رزرو توسط ورزشکار فقط رزرو خودش؛ منشی/مدیر همچنان می‌توانند لغو کنند.
- برچسب آقایان/بانوان/مختلط فقط نمایشی است؛ سیستم بر اساس جنسیت رد نمی‌کند.
- امنیت: مخفی کردن دکمه در UI کافی نیست؛ سرور member_id را از سشن ورزشکار بگیرد.

# DoD
- تست‌های مرتبط سبز.
- بدون .env / secrets در گیت.
- seed جعلی کافی برای دمو.
- بعد از سبز بودن: commit و push به origin/main طبق قانون پروژه Gym.
- به صاحب گزارش بده: کاملاً OK یا ناقص با جزئیات.

# خروجی گزارش
چه APIهایی اضافه شد، کجای UI، چطور با seed تست شود (موبایل/رمز ورزشکار)، و چه چیزی خارج ماند.
```
