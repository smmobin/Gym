# پرامپت مرحلهٔ بعد — برای چت سازنده (Agent)

آخرین به‌روزرسانی: ۱۴۰۴-۰۷-۲۷ (مدیر محصول — پس از تأیید رزرو کلاس ورزشکار)  
مرحلهٔ کدنویسی اختیاری بعدی: **درگاه پرداخت آنلاین (sandbox-ready)**

اگر صاحب هنوز دیپلوی نکرده: اول کار دستی طبق `docs/guides/deploy.md` و `backup.md`.  
اگر صاحب پیامک را قبل از درگاه می‌خواهد: در چت مدیر محصول بگوید تا پرامپت پیامک جایگزین شود.

متن زیر را **کامل کپی** کن و در چت Agent سازنده بفرست.

---

```text
# نقش
تو Agent سازندهٔ GYM CONTROL هستی (نه مدیر محصول).
docs را خودت از docs/README.md پیدا کن و بخوان.
منبع حقیقت: docs/product/business-rules.md (پول + ورزشکار + placeholder درگاه) و docs/guides/security.md.
کار جدید فقط در frontend/ و backend/. HTML ریشه / GitHub Pages را دست نزن.
هیچ کلید API، مرچنت‌کد، یا .env واقعی در گیت نرود.

# زمینهٔ فعلی (در کد تأیید کن)
- روش پرداخت online در enum و UI هست ولی به درگاه وصل نیست؛ لیبل «آنلاین (بدون درگاه)».
- ورزشکار می‌تواند «درخواست تمدید» بزند → فقط اعلان desk؛ تمدید خودکار بعد از پرداخت موفق هنوز نیست.
- میز می‌تواند پرداخت نقدی/کارت/انتقال ثبت کند؛ برگشت و رسید و audit مالی هست.
- رزرو کلاس ورزشکار و freeze انجام شده‌اند — این برش به آن‌ها کاری ندارد.

# هدف این برش (یک vertical slice)
اتصال امن به یک درگاه ایرانی رایج با حالت sandbox/test، طوری که:
1) ورزشکار لاگین‌شده بتواند برای تمدید/پرداخت بدهی خودش یک پرداخت online شروع کند.
2) پس از تأیید موفق درگاه (callback/verify سروری)، سیستم پرداخت را paid ثبت کند و اگر هدف تمدید بوده، عضویت را طبق قوانین renew موجود بسازد/تمدید کند.
3) در UI کارکنان و ورزشکار مشخص باشد که درگاه فعال است (sandbox) یا هنوز پیکربندی نشده.

Provider پیشنهادی پیش‌فرض: زرین‌پال (Zarinpal) با API رسمی فعلی‌شان؛ اگر در کد/deps محدودیت بود، یک adapter واحد بنویس تا بعداً عوض شود. نام provider را در تنظیمات/env قابل‌تعویض نگه دار.

# داخل محدوده
Backend:
- تنظیمات فقط از env (مثال نام‌ها؛ با الگوی Settings موجود پروژه هم‌خوان کن):
  - PAYMENT_GATEWAY_PROVIDER=zarinpal|none
  - PAYMENT_GATEWAY_MERCHANT_ID=...
  - PAYMENT_GATEWAY_SANDBOX=true|false
  - PAYMENT_GATEWAY_CALLBACK_URL=... (HTTPS در prod)
- اگر provider=none یا merchant خالی: رفتار فعلی «هنوز آماده نیست» بماند (۴۰۳/۴۰۰ واضح فارسی).
- جریان:
  - ایجاد payment با status مناسب (مثلاً pending) + amount توافقی + member فقط از سشن ورزشکار (یا desk اگر مسیر میز هم اضافه کردی — حداقل مسیر ورزشکار الزامی است).
  - redirect/authority از درگاه؛ ذخیرهٔ شناسهٔ تراکنش درگاه روی ردیف پرداخت (فیلد جدید فقط اگر لازم).
  - endpoint callback/verify که فقط سرور verify کند (هرگز به verify کلاینت اعتماد نکن).
  - موفقیت: status=paid، receipt طبق سرویس موجود، audit log مالی، سپس renew طبق سرویس billing موجود (reuse؛ منطق تاریخ شروع از end_date را دوباره ننویس).
  - شکست/انصراف: pending نماند بی‌پایان؛ وضعیت failed/cancelled واضح؛ بدون ساخت عضویت.
- Authz: ورزشکار فقط برای خودش؛ میز طبق نقش‌های موجود billing؛ بدون افشای دادهٔ عضو دیگر.
- Idempotency: تکرار callback همان authority نباید دوبار عضویت/رسید بسازد.
- تست: pytest با mock درگاه (بدون شبکهٔ واقعی در CI)؛ happy path + verify fail + duplicate callback + gateway disabled.

Frontend:
- پنل /athlete: به‌جای فقط «درخواست تمدید»، اگر درگاه پیکربندی شده مسیر «پرداخت آنلاین (آزمایشی)» نشان بده؛ وگرنه همان پیام آماده نیست + درخواست تمدید.
- /billing: لیبل online را از «بدون درگاه» به وضعیت واقعی بر اساس قابلیت سرور به‌روز کن (یک GET کوچک تنظیمات عمومی غیرحساس یا فلگ از API موجود).
- RTL فارسی؛ مبلغ تومان؛ بدون نمایش کلید.
- vitest برای نمایش حالت فعال/غیرفعال و شروع جریان (mock API).

Seed / docs:
- در getting-started کوتاه بنویس چطور با sandbox و env تست شود.
- نمونهٔ .env.example (اگر در پروژه هست) با کلیدهای خالی و توضیح؛ مقدار واقعی نگذار.

# خارج از محدوده (صریح — نساز)
- پیامک واقعی / OTP (برش جدا).
- ذخیرهٔ شماره کارت / CVV / ذخیرهٔ کارت برای استفادهٔ بعدی.
- waitlist کلاس، چندشعبه، فروشگاه کالا.
- بازنویسی HTML پروتوتایپ ریشه.
- دیپلوی با credential صاحب روی اکانت واقعی‌اش (فقط docs/env نمونه).
- عوض کردن قوانین قیمت گذشته یا بازنویسی پرداخت‌های paid قدیمی.
- کیف پول داخلی پیچیده.

# قوانین کسب‌وکار مرتبط (خلاصه)
- درآمد گزارش = فقط پرداخت‌شده؛ بدهی جدا.
- پرداخت ثبت‌شده ویرایش نشود؛ اصلاح = برگشت + پرداخت جدید.
- قیمت طرح فعلی سوابق گذشته را عوض نمی‌کند؛ مبلغ توافقی روی همان تراکنش.
- وقتی درگاه آماده شد: ورزشکار می‌تواند تمدید کند و پس از پرداخت موفق، تمدید خودکار شود.
- امنیتی: سرور enforce کند؛ مخفی کردن UI کافی نیست؛ secrets فقط env.

# DoD
- تست‌های مرتبط سبز (pytest + vitest).
- بدون secrets در گیت.
- اگر gateway خاموش است، رفتار قبلی نشکند.
- بعد از سبز: commit و push به origin/main طبق قانون Gym.
- گزارش به صاحب: کاملاً OK یا ناقص + چطور با sandbox تست کند.

# خروجی گزارش
APIها، فیلدهای جدید، نام envها، مسیر UI ورزشکار/میز، و آنچه عمداً نساختی (پیامک و …).
```
