# پرامپت مرحلهٔ بعد — برای چت سازنده (Agent)

آخرین به‌روزرسانی: ۱۴۰۴-۰۷-۲۳ (مدیر محصول — پس از تأیید مدل/seed)  
مرحله: احراز هویت کارکنان (موبایل + رمز) + نشست امن + نقش سمت سرور

کل بلاک زیر را کپی کن و در یک **چت Agent جدید** (سازنده، نه مدیر محصول) بفرست.

```text
# نقش
تو Agent سازندهٔ پروژهٔ GYM CONTROL هستی. مدیر محصول این مرحله را تأیید کرده.
docs و قوانین را خودت پیدا و بخوان (از docs/README.md شروع کن).
منبع حقیقت رفتار: docs/product/business-rules.md
امنیت: docs/guides/security.md — اگر با حدس شخصی تعارض داشت، docs مقدم است.
کار جدید فقط در frontend/ و backend/. پروتوتایپ HTML ریشه را تغییر نده.

# زبان با صاحب پروژه
فارسی، ساده، داخل <div dir="rtl">. اصطلاح فنی را یک جمله توضیح بده.
در پایان بگو کاملاً OK یا ناقص + نتیجهٔ تست.

# هدف این چت (فقط همین برش)
ورود واقعی کارکنان باشگاه تا سرور بداند کیست و چه نقشی دارد.

1) لاگین با موبایل + رمز (حداقل ۸ کاراکتر)
2) خروج واقعی (باطل‌کردن نشست سمت سرور)
3) endpoint «من کیستم» (me) برای فرانت
4) وابستگی‌های FastAPI برای «کاربر فعلی» و «فقط این نقش‌ها»
5) حداقل یک صفحهٔ ورود ساده در React (فارسی/RTL) که به API وصل شود و بعد از ورود وضعیت کاربر را نشان دهد + دکمه خروج
6) به‌روز کردن seed تا رمزها با همان الگوریتم hash واقعی auth هش شوند (الان seed placeholder دارد)
7) تست خودکار سبز: موفق، رمز غلط، بدون نشست → 401، نقش اشتباه → 403، خروج، حداقل طول رمز

# داخل محدوده
Backend:
- POST /api/v1/auth/login  body: mobile, password
- POST /api/v1/auth/logout
- GET  /api/v1/auth/me     (نیاز به نشست معتبر)
- یک endpoint نمونهٔ محافظت‌شده برای تست نقش، مثلاً:
  GET /api/v1/auth/staff-ping  فقط manager + receptionist
  (یا معادل واضح؛ مهم تست 403 برای trainer است)
- جدول یا ذخیرهٔ نشست سمت سرور (session id در cookie؛ نشست در DB یا store معادل قابل‌باطل‌شدن)
- Cookie: HttpOnly؛ SameSite مناسب توسعهٔ local؛ Secure فقط وقتی محیط production/HTTPS است (در local خاموش باشد تا روی http://127.0.0.1 کار کند)
- hash رمز: bcrypt یا Argon2 (کتابخانهٔ رایج و نگهداری‌شده). متن خام رمز هرگز در DB نباشد
- rate limit ساده روی login (حتی در حافظه برای MVP محلی قابل قبول است؛ بیش‌ازحد مهندسی نکن)
- CORS طوری که فرانت Vite با credentials بتواند cookie بفرستد
- مدیر بتواند رمز یک کاربر کارکنان را عوض کند: حداقل API
  POST یا PATCH /api/v1/auth/users/{id}/password  فقط role=manager
  (بدون پیامک؛ مطابق business-rules)
- کاربران seed موجود (موبایل‌های 09120000001…04 و نقش‌های manager/receptionist/trainer) باید بعد از seed با رمز توسعهٔ شناخته‌شده وارد شوند؛ رمز را در docs/getting-started به‌صورت «فقط توسعه» بنویس، نه به‌عنوان رمز واقعی باشگاه

Frontend:
- صفحهٔ ورود ساده (موبایل + رمز + خطا به فارسی)
- بعد از ورود: نام و نقش را نشان بده + خروج
- نیازی به داشبورد کامل منشی/مدیر/مربی نیست
- RTL و فارسی حفظ شود؛ تم را پیچیده نکن — با اسکلت فعلی هماهنگ بمان

Docs:
- docs/guides/getting-started.md: چطور لاگین توسعه را امتحان کنند
- docs/product/roadmap-status.md را فقط اگر مطمئنی «auth انجام شد» علامت بزن؛ وگرنه مدیر محصول بعداً به‌روز می‌کند

# خارج از محدوده (نساز)
- لاگین ورزشکار / پنل ورزشکار
- CRUD اعضا، حضور، پرداخت، کلاس، کمد
- پنل کامل React نقش‌ها
- پیامک، فراموشی رمز با پیامک، درگاه پرداخت
- تغییر HTML ریشه / GitHub Pages پروتوتایپ
- Docker کامل، جدا کردن ریپو
- Dependabot مگر برای رفع آسیب‌پذیری مسدودکنندهٔ همین برش

# قوانین کسب‌وکار مرتبط (اجرا کن)
- ورود کارکنان: موبایل + رمز؛ رمز حداقل ۸ کاراکتر
- نقش‌ها: manager / receptionist / trainer (ورزشکار در این برش نه)
- فراموشی رمز نسخهٔ اول: فقط مدیر رمز را عوض می‌کند (بدون پیامک)
- مخفی کردن UI امنیت نیست؛ مجوز روی سرور enforce شود
- اولین مدیر از قبل در seed هست؛ ساخت UI «ثبت‌نام عمومی» نساز

# کیفیت و امنیت
- پیشوند API: /api/v1
- هیچ .env یا رمز واقعی در گیت نباشد
- تست pytest برای مسیرهای بالا؛ vitest اگر برای فرانت لاگین منطقی است حداقل یک تست کوچک
- بعد از تست سبز: commit و push به origin/main طبق قانون پروژه Gym
- گزارش به صاحب: چه endpointهایی، چطور cookie کار می‌کند، حساب‌های seed برای تست، چه چیزی عمداً ساخته نشد
```
