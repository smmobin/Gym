# پرامپت مرحلهٔ بعد — برای چت سازنده (Agent)

آخرین به‌روزرسانی: ۱۴۰۴-۰۷-۲۷ (مدیر محصول — پس از تأیید مهمان/آزمایشی)  
مرحله: تنظیمات باشگاه + اعلان داخل‌برنامه + placeholder پیامک/درگاه

کل بلاک زیر را کپی کن و در یک **چت Agent جدید** (سازنده، نه مدیر محصول) بفرست.

---

```text
# نقش
تو Agent سازندهٔ پروژهٔ GYM CONTROL هستی. مدیر محصول این مرحله را تأیید کرده.
docs را خودت پیدا و بخوان (از docs/README.md شروع کن).
منبع حقیقت: docs/product/business-rules.md بخش‌های ۱۱ (اعلان/پیامک) و ۱۲٫۱ (تنظیمات).
مدل موجود:
- GymSettings (یک ردیف منطقی باشگاه آذر): نام، تلفن، نشانی، day_end_time، expiry_warning_days، freeze_annual_cap_days، working_hours_note، renewal_rules_note
- جدول اعلان هنوز نیست — باید بسازی
کار جدید فقط در frontend/ و backend/. پروتوتایپ HTML ریشه را تغییر نده.
لاگین ورزشکار نساز. پیامک واقعی و درگاه واقعی نساز.

# زبان با صاحب پروژه
فارسی، ساده، داخل <div dir="rtl">.
در پایان بگو کاملاً OK یا ناقص + نتیجهٔ تست.

# هدف این چت (فقط همین برش)
1) مدیر بتواند تنظیمات باشگاه را ببیند و ویرایش کند
2) کارکنان اعلان داخل‌برنامه ببینند (حداقل: انقضای نزدیک، بدهی، فرم آزمایشی جدید؛ درخواست تمدید اگر داده نداری ساده/placeholder)
3) UI پیامک: قالب + دکمهٔ مرده + متن «هنوز آماده نیست»
4) روش پرداخت آنلاین از قبل در billing هست؛ اگر جایی دکمهٔ «پرداخت آنلاین/درگاه» هست یا لازم است، صریحاً غیرفعال + همان پیام
5) تست سبز

# داخل محدوده

## الف) تنظیمات باشگاه
Backend:
- GET /gym-settings  — staff لاگین‌شده می‌تواند بخواند (منشی برای day_end و هشدار انقضا مفید است)
- PUT یا PATCH /gym-settings  — فقط manager
  فیلدها مطابق مدل؛ لوگو فایل نساز
- اگر ردیف نیست، هنگام GET بساز با پیش‌فرض‌ها (یا از seed اطمینان بده یک ردیف هست)
- تغییر تنظیمات حساس → ترجیحاً یک audit_log ساده

Frontend:
- صفحهٔ /settings فقط برای مدیر (منشی اگر باز کرد پیام عدم دسترسی؛ سرور ۴۰۳ روی نوشتن)
- فرم ساده RTL

اختیاری ولی مفید: attendance از day_end_time تنظیمات بخواند اگر الان hardcode است — فقط اگر ارزان و تست‌شده.

## ب) اعلان داخل‌برنامه
مدل پیشنهادی staff_notifications یا notifications:
- id, user_id? (null = همهٔ desk), role_audience? (manager/receptionist/all_staff), kind, title, body, entity_type?, entity_id?, is_read, created_at
یا ساده‌تر: اعلان‌های سراسری desk بدون per-user در v1 + is_read per user در جدول جانبی — یک طراحی ساده انتخاب و مستند کن.

حداقل kindها:
- trial_lead_new (وقتی POST عمومی trial موفق شد)
- membership_expiring (اعضایی که end_date تا expiry_warning_days آینده است) — می‌تواند job سبک هنگام GET /notifications تولید/به‌روز شود نه کرون اجباری
- member_debt (بدهی > 0) — خلاصه/نمونه نه اسپم بی‌نهایت؛ یا فقط وقتی از آستانه گذشت؛ ساده بگیر
- renewal_request — اگر هنوز دادهٔ ورزشکار نیست، فقط قالب UI یا seed نمونه

API:
- GET /notifications  (کارکنان) — لیست جدیدها/خوانده‌نشده
- POST /notifications/{id}/read  یا POST /notifications/read-all
- ایجاد اعلان trial در سرویس trial_leads هنگام ثبت عمومی

Frontend:
- زنگوله/لیست در شل بعد از لاگین
- لینک به /trial-leads یا عضو مربوط اگر entity معلوم است

## ج) Placeholder پیامک و درگاه
- صفحه یا بخش کوچک /sms-templates (مدیر یا desk): چند قالب متنی ثابت (انقضا، خوش‌آمد، بدهی) + دکمهٔ «ارسال» disabled + متن «هنوز آماده نیست»
- هیچ SDK پیامک، هیچ API کلید، هیچ .env پیامک در گیت
- در billing اگر online انتخاب می‌شود، از قبل بدون درگاه است؛ یک جملهٔ UI کافی است که به درگاه وصل نیست

# خارج از محدوده (نساز)
- لاگین ورزشکار / پنل ورزشکار
- پیامک واقعی، درگاه واقعی، وب‌هوک بانک
- آپلود لوگو
- کرون پیچیدهٔ سرور (تولید اعلان روی خواندن/رویداد کافی است)
- تغییر HTML ریشه
- فروشگاه / چند شعبه

# قوانین کسب‌وکار مرتبط (اجرا کن)
- تنظیمات: نام، تلفن، نشانی، ساعت کاری، قوانین تمدید، روز هشدار انقضا، ساعت پایان روز، سقف freeze از نسخهٔ اول
- اعلان داخل برنامه برای کارکنان: انقضا، درخواست تمدید، بدهی، فرم آزمایشی
- پیامک: فقط قالب + دکمهٔ مرده + «هنوز آماده نیست»
- مخفی کردن UI امنیت نیست — سرور نقش را enforce کند

# کیفیت
- pytest: manager تنظیمات را عوض می‌کند؛ receptionist نوشتن ۴۰۳؛ خواندن OK؛ trial عمومی اعلان می‌سازد؛ GET notifications؛ mark read؛ ۴۰۱
- vitest کوچک اگر منطقی است
- seed: تنظیمات + چند اعلان نمونه
- .env و دادهٔ واقعی در گیت نباشد
- بعد از تست سبز: commit + push به origin/main
- گزارش: endpointها، مدل اعلان، آیا attendance به day_end وصل شد، صفحات UI، چه چیز عمداً نساختی

# اگر مبهم شد
حدس نزن. business-rules را اجرا کن. جزئیات فرعی را ساده بگیر و مستند کن.
```
