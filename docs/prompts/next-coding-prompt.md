# پرامپت مرحلهٔ بعد — برای چت سازنده (Agent)

آخرین به‌روزرسانی: ۱۴۰۴-۰۷-۲۷ (مدیر محصول — پس از تأیید مربی/برنامه)  
مرحله: غیبت کلاس رزروشده → مصرف یک جلسه از بسته

کل بلاک زیر را کپی کن و در یک **چت Agent جدید** (سازنده، نه مدیر محصول) بفرست.

---

```text
# نقش
تو Agent سازندهٔ پروژهٔ GYM CONTROL هستی. مدیر محصول این مرحله را تأیید کرده.
docs را خودت پیدا و بخوان (از docs/README.md شروع کن).
منبع حقیقت: docs/product/business-rules.md بخش کلاس گروهی (جملهٔ غیبت) + حضور (مصرف جلسه).
زیرساخت موجود:
- ClassBooking + BookingStatus: booked / cancelled / attended / no_show
- helper ظرفیت فقط status=booked را می‌شمارد → با تغییر به no_show/attended جا آزاد می‌شود
- حضور check-in با type=class الان sessions_remaining را برای بستهٔ جلسه‌ای کم می‌کند — منطق غیبت را با آن هم‌خوان نگه دار (دوبار کم نشود برای همان رزرو)
- صفحهٔ /classes و API group-classes موجود است
کار جدید فقط در frontend/ و backend/. پروتوتایپ HTML ریشه را تغییر نده.

# زبان با صاحب پروژه
فارسی، ساده، داخل <div dir="rtl">.
در پایان بگو کاملاً OK یا ناقص + نتیجهٔ تست.

# هدف این چت (فقط همین برش)
منشی/مدیر بتوانند برای رزرو کلاس که عضو نیامده، «غیبت (no_show)» ثبت کنند تا:
1) یک جلسه از بستهٔ مناسب class کم شود
2) وضعیت رزرو no_show شود و ظرفیت آزاد گردد (دیگر booked نباشد)
3) اگر بستهٔ منطبق واضح نبود، با هشدار membership_id را انتخاب کنند
4) ثبت تکراری غیبت روی همان رزرو جلسه را دوباره کم نکند

حداقل UI: از صفحهٔ /classes روی لیست رزروهای یک کلاس، دکمهٔ «حاضر شد» / «غیبت» (attended اختیاری ولی مفید؛ no_show اجباری این برش).

# داخل محدوده
Backend (/api/v1) — پیشنهاد:

- POST /group-classes/{class_id}/bookings/{booking_id}/no-show
  body اختیاری: membership_id? (اگر چند بسته یا ابهام)
  قوانین:
  - فقط manager+receptionist (trainer → ۴۰۳ مگر سیاست ساده‌تر؛ پیش‌فرض desk-only)
  - رزرو باید status=booked باشد؛ در غیر این صورت ۴۰۹
  - ترجیحاً فقط بعد از شروع/پایان کلاس (starts_at گذشته) اجازه بده؛ اگر سخت است: همیشه اجازه بده ولی در گزارش بنویس — پیشنهاد: ends_at گذشته یا starts_at گذشته (یک سیاست انتخاب و مستند کن)
  - یک جلسه از عضویت جلسه‌ای مناسب کم کن (sessions_remaining -= 1، نه زیر صفر)
  - انتخاب بسته: اولویت با membership فعال که session_count/sessions_remaining برای class معنا دارد؛ اگر فقط یکی → همان؛ اگر چند یا هیچ → اگر membership_id نیامده ۴۰۰ با لیست گزینه‌ها/هشدار؛ اگر آمده همان را مصرف کن
  - status → no_show
  - اگر قبلاً با check-in type=class برای همان روز/کلاس جلسه کم شده، دوباره کم نکن (یک ارتباط ساده: اگر attendance مرتبط هست یا فلگ روی booking — ساده‌ترین راه امن را انتخاب و تست کن)

- POST …/bookings/{booking_id}/attended  (اختیاری ولی توصیه‌شده)
  - status → attended بدون کم کردن جلسهٔ اضافه اگر check-in قبلاً کم کرده؛ یا اگر ورود جدا ثبت نشده، یک جلسه کم کن مثل type=class — یک سیاست یکنواخت انتخاب و مستند کن
  - هدف: رزرو از booked خارج شود تا ظرفیت درست بماند

نقش‌ها: بدون لاگین ۴۰۱؛ trainer پیش‌فرض ۴۰۳ روی no-show.

Frontend:
- در /classes: جزئیات رزروها + دکمهٔ غیبت (+ حاضر اگر ساختی)
- اگر API گفت membership_id لازم است، انتخابگر عضویت با هشدار نشان بده
- RTL/فارسی؛ پیام خطای واضح

Docs:
- getting-started: چطور غیبت کلاس را امتحان کنند
- schema-todos: ردیف «مصرف جلسه برای غیبت کلاس» را به‌روز کن
- roadmap فقط اگر مطمئنی تمام شد

# خارج از محدوده (نساز)
- قفل پرونده، گزارش سود مدیر، مهمان روزانه، فرم آزمایشی
- لاگین ورزشکار، پیامک، درگاه
- لیست انتظار / overbook
- پنل مربی بیشتر، کمد بیشتر
- کرون پیچیدهٔ «خودکار همهٔ غایب‌ها» — اگر خیلی ارزان است به‌عنوان اختیاری؛ پیش‌فرض دستی توسط منشی کافی است
- تغییر HTML ریشه

# قوانین کسب‌وکار مرتبط (اجرا کن)
- غیبت در کلاس رزروشده: یک جلسه از بستهٔ مخصوص همان کلاس/رشته مصرف می‌شود
- اگر بستهٔ منطبق نبود منشی با هشدار انتخاب می‌کند
- جا بعد از ساعت کلاس آزاد است (وضعیت دیگر booked نباشد)
- مخفی کردن UI امنیت نیست

# کیفیت
- pytest: no-show جلسه کم می‌کند؛ تکرار no-show دوباره کم نمی‌کند؛ بدون بسته/ابهام بدون membership_id رد؛ با membership_id OK؛ ظرفیت بعد از no-show آزاد؛ ۴۰۱/۴۰۳
- vitest کوچک اگر منطقی است
- .env و دادهٔ واقعی در گیت نباشد
- بعد از تست سبز: commit + push به origin/main
- گزارش: endpointها، سیاست زمان مجاز no-show، سیاست attended، جلوگیری از double-deduct، چه چیز عمداً نساختی

# اگر مبهم شد
حدس نزن. business-rules را اجرا کن. جزئیات فرعی را ساده بگیر و مستند کن.
```
