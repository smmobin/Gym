## هدف
در لیست انتخاب عضو هنگام **واگذاری کمد** (`#lockers` → member-pick با `showLockerEligibility`)، اگر عضو الان کمد فعال دارد، این وضعیت **واضح دیده شود** تا منشی دوباره همان نفر را برای کمد جدید انتخاب نکند.

الان سرور هنگام assign اگر عضو کمد داشته باشد → ۴۰۹ با پیام «این عضو الان کمد دارد (کد)…»، ولی در UI فقط badgeهای «می‌تواند / نمی‌تواند کمد بگیرد» بر اساس `can_receive_locker` (طرح شامل‌کمد) است و **کمد فعلی را نشان نمی‌دهد**.

## تصمیم محصول
- در picker کمد، اولویت نمایش:
  1) اگر واگذاری فعال دارد → badge واضح مثل «کمد دارد (L-01)» (رنگ warn یا خنثی متمایز؛ نه سبز «می‌تواند»)
  2) وگرنه مثل الان: «می‌تواند کمد بگیرد» / «نمی‌تواند کمد بگیرد»
- عضو دارای کمد **قابل انتخاب برای assign جدید نباشد** (دکمه/ردیف غیرفعال یا کلیک بی‌اثر + عنوان/hint کوتاه: اول همان کمد را آزاد کنید). از لیست حذف کامل نکن — باید دیده شود.
- کد کمد در badge بیاید اگر معلوم است.
- pickerهای دیگر (مالی، پیامک، …) که `showLockerEligibility` ندارند رفتار فعلی را حفظ کنند مگر فیلد جدید بی‌ضرر باشد.

## داخل محدوده

### ۱) API لیست/سریالایز عضو
- روی `MemberOut` (یا معادل) فیلد(های) واضح اضافه کن، مثلاً:
  - `has_active_locker: bool`
  - `current_locker_code: str | null` (کد کمد فعال؛ اگر ندارد null)
- در `serialize_member` / `serialize_members` با یک query کارآمد روی `locker_assignments` باز (مثلاً `released_at IS NULL`) برای همان batch اعضا پر کن — N+1 نزن.
- `can_receive_locker` معنی فعلی‌اش بماند (واجد طرح شامل‌کمد)؛ منطق «الان کمد دارد» جدا باشد.
- تست pytest: عضوی با assignment فعال در لیست اعضا `has_active_locker=true` و کد درست؛ بدون assignment → false/null. تست assign موجود ۴۰۹ را نشکن.

### ۲) UI picker (`renderMemberPick` در `ui.js` + مصرف در `lockers.js`)
- وقتی `showLockerEligibility: true`:
  - اگر `has_active_locker` → badge «کمد دارد (CODE)»؛ ردیف `disabled` / کلاس `is-disabled`؛ `onPick` صدا زده نشود.
  - وگرنه همان badge can/cannot فعلی.
- استایل با badgeهای موجود Ocean Dark هم‌خوان؛ در صورت نیاز کلاس کوچک در CSS پنل.
- تست vitest در `member-pick.test.js`: عضو با کمد فعال متن «کمد دارد» + کد؛ کلیکش pick نکند؛ عضو بدون کمد مثل قبل.

### ۳) docs کوتاه
- یک خط در `business-rules.md` بخش کمد: هر عضو حداکثر یک کمد فعال؛ در UI واگذاری، دارندگان کمد مشخص و غیرقابل انتخاب مجدد تا آزادسازی.
- در صورت نیاز یک خط در getting-started چک‌لیست کمد.
