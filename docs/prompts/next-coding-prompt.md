## پرامپت B — درگاه پرداخت آنلاین (sandbox)

```text
# نقش
تو Agent سازندهٔ GYM CONTROL هستی (نه مدیر محصول).
docs را خودت از docs/README.md پیدا کن و بخوان.
منبع حقیقت: docs/product/business-rules.md (پول + ورزشکار + placeholder درگاه) و docs/guides/security.md.
فرض قطعی: ورود یکپارچه و پنل مربی از قبل آماده‌اند — آن‌ها را بازنویسی نکن مگر باگ blocker.
کار جدید فقط در frontend/ + backend/. ظاهر = Ocean Dark MPA (ADR 0005). React برنگردان.
هیچ کلید API، مرچنت‌کد، یا .env واقعی در گیت نرود.

# زمینهٔ فعلی (در کد تأیید کن)
- روش پرداخت online در enum و UI هست ولی به درگاه وصل نیست.
- ورزشکار می‌تواند «درخواست تمدید» بزند → فقط اعلان desk؛ تمدید خودکار بعد از پرداخت موفق هنوز نیست.
- میز پرداخت نقدی/کارت/انتقال ثبت می‌کند؛ برگشت و رسید و audit مالی هست.
- فرانت محصول: frontend/ (login, receptionist, manager, trainer, athlete).

# هدف این برش (یک vertical slice)
اتصال امن به یک درگاه ایرانی رایج با حالت sandbox/test، طوری که:
1) ورزشکار لاگین‌شده بتواند برای تمدید/پرداخت بدهی خودش یک پرداخت online شروع کند.
2) پس از تأیید موفق درگاه (callback/verify سروری)، سیستم پرداخت را paid ثبت کند و اگر هدف تمدید بوده، عضویت را طبق قوانین renew موجود بسازد/تمدید کند (reuse سرویس billing؛ منطق end_date را دوباره ننویس).
3) در UI ورزشکار و میز مشخص باشد که درگاه فعال است (sandbox) یا هنوز پیکربندی نشده.
4) اگر gateway خاموش/بدون merchant: همان «هنوز آماده نیست» + درخواست تمدید desk بماند و رفتار فعلی نشکند.

Provider پیشنهادی پیش‌فرض: زرین‌پال با API رسمی فعلی؛ یک adapter واحد بنویس تا بعداً عوض شود. نام provider در env قابل‌تعویض.

# داخل محدوده
Backend:
- تنظیمات فقط از env (نام‌ها را با Settings موجود پروژه هم‌خوان کن)، مثلاً:
  - PAYMENT_GATEWAY_PROVIDER=zarinpal|none
  - PAYMENT_GATEWAY_MERCHANT_ID=...
  - PAYMENT_GATEWAY_SANDBOX=true|false
  - PAYMENT_GATEWAY_CALLBACK_URL=... (HTTPS در prod)
- اگر provider=none یا merchant خالی → ۴۰۳/۴۰۰ فارسی واضح؛ UI «آماده نیست».
- جریان:
  - ایجاد payment با status مناسب (مثلاً pending) + مبلغ توافقی؛ member فقط از سشن ورزشکار (مسیر ورزشکار الزامی است؛ مسیر میز اختیاری).
  - redirect/authority از درگاه؛ ذخیرهٔ شناسهٔ تراکنش روی ردیف پرداخت (فیلد جدید فقط اگر لازم).
  - endpoint callback/verify: فقط سرور verify کند (هرگز به کلاینت اعتماد نکن).
  - موفقیت: status=paid، receipt طبق سرویس موجود، audit مالی، سپس renew در صورت هدف تمدید.
  - شکست/انصراف: failed/cancelled واضح؛ بدون ساخت عضویت.
- Authz: ورزشکار فقط خودش؛ بدون افشای عضو دیگر.
- Idempotency: تکرار callback همان authority → دوبار عضویت/رسید نسازد.
- تست: pytest با mock درگاه (بدون شبکه در CI)؛ happy path + verify fail + duplicate callback + gateway disabled.

Frontend (Ocean Dark):
- پنل /athlete/: اگر درگاه پیکربندی شده مسیر «پرداخت آنلاین (آزمایشی)»؛ وگرنه پیام آماده نیست + درخواست تمدید.
- میز/billing: لیبل online را بر اساس فلگ غیرحساس سرور به‌روز کن.
- RTL فارسی؛ مبلغ تومان؛ بدون نمایش کلید.
- تست دود فرانت (mock API) برای حالت فعال/غیرفعال.

Seed / docs:
- getting-started: چطور با sandbox و env تست شود.
- .env.example با کلیدهای خالی و توضیح؛ مقدار واقعی نگذار.
- roadmap-status و schema-todos را بعد از اتمام به‌روز کن.

# خارج از محدوده (صریح)
- پیامک واقعی / OTP
- ذخیرهٔ شماره کارت / CVV / کارت ذخیره‌شده
- waitlist کلاس، چندشعبه، فروشگاه کالا
- بازنویسی HTML ماکت ریشه برای GitHub Pages مگر لازم برای لینک
- دیپلوی با credential صاحب
- عوض کردن قوانین قیمت گذشته یا ویرایش پرداخت‌های paid قدیمی
- دستکاری ورود یکپارچه / پنل مربی مگر باگ blocker

# قوانین کسب‌وکار مرتبط (خلاصه)
- درآمد گزارش = فقط پرداخت‌شده؛ بدهی جدا.
- پرداخت ثبت‌شده ویرایش نشود؛ اصلاح = برگشت + پرداخت جدید.
- قیمت طرح فعلی سوابق گذشته را عوض نمی‌کند؛ مبلغ توافقی روی همان تراکنش.
- وقتی درگاه آماده شد: ورزشکار می‌تواند تمدید کند و پس از پرداخت موفق، تمدید خودکار شود.
- امنیت: سرور enforce کند؛ secrets فقط env.

# DoD

- بدون secrets در گیت.
- اگر gateway خاموش است، رفتار قبلی نشکند.
- بعد از سبز: commit و push به origin/main طبق قانون Gym.
- گزارش به صاحب: کاملاً OK یا ناقص + چطور با sandbox تست کند + نام envها و APIها.
```
