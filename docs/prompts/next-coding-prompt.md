## هدف
صاحب باشگاه می‌بیند اشتراک‌ها «در انتظار» مانده‌اند و فکر می‌کند پول پرداخت نشده؛ در حالی که:
1) مبلغ روی کارت = `agreed_amount` عضویت است نه وضعیت رسید پرداخت؛
2) وضعیت `pending` عضویت اغلب یعنی **بازه هنوز شروع نشده** (تمدید آینده)، نه «پرداخت verify نشده»؛
3) وقتی تاریخ شروع می‌رسد، سیستم امروز وضعیت را خودکار به `active` عوض نمی‌کند → اشتراک‌های پرداخت‌شده ممکن است تا ابد pending بمانند.

باید: (الف) وضعیت تاریخ‌محور را هم‌تراز تقویم تهران نگه داری؛ (ب) برچسب UI را طوری عوض کنی که با «پرداخت در انتظار» قاطی نشود.

## تصمیم محصول
- عضویت با `status=pending` و `start_date <= امروز تهران <= end_date` باید به `active` تبدیل شود (حداقل هنگام خواندن لیست/جزئیات و مسیرهای حساس مثل حضور/بدهی؛ ترجیح: یک تابع مشترک `refresh_membership_status` / `sync_membership_window`).
- اگر `end_date < امروز` و وضعیت هنوز `pending` یا `active` (و نه cancelled/frozen طبق قوانین موجود) → به `expired` (با احترام به freeze: عضویت `frozen` را بی‌خود expire نکن مگر قانون فعلی freeze همین را بگوید — رفتار freeze موجود را نشکن).
- برچسب فارسی عضویت:
  - برای `pending` وقتی شروع در آینده است: ترجیح **«شروع‌نشده»** یا **«از تاریخ …»** — نه «در انتظار» Alone که شبیه پرداخت است.
  - وضعیت پرداخت (`payment.status=pending`) برچسب جدا بماند («در انتظار» برای پرداخت آنلاین OK است).
- روی کارت اشتراک ورزشکار/میز: مبلغ را اگر لازم است با برچسب کوتاه مثل «مبلغ توافقی» روشن کن تا با «پرداخت‌شده» اشتباه نشود (حداقلی؛ redesign بزرگ نکن).
- پرداخت `paid` به‌تنهایی عضویت future-start را active نکند (درست است)؛ فقط تقویم وضعیت را جلو می‌برد.

## داخل محدوده

### ۱) بک‌اند — همگام‌سازی وضعیت بازه
- در سرویس billing (یا ماژول membership مناسب): تابعی بنویس که برای یک یا چند `Membership` با `today_tehran()`:
  - pending + داخل بازه → active
  - active (یا pending) + بعد از end و غیر cancelled/frozen → expired (با قوانین فعلی سازگار)
- این تابع را صدا بزن حداقل در:
  - `list_member_memberships` / API لیست عضویت عضو (میز)
  - مسیر athlete برای «اشتراک من» اگر جداست
  - در صورت امکان قبل از چک حضور/بدهی وابسته به active (اگر الان pending مانع ورود اشتباه می‌شود)
- بعد از تغییر وضعیت، در صورت نیاز `member.status` را مثل renew فعلی هم‌خوان کن (عضو pending → active وقتی عضویت active شد).
- audit سبک اختیاری است؛ اگر می‌نویسی action واضح مثل `membership.window_sync`؛ اسپم audit روی هر GET نزن مگر یک‌بار واقعی تغییر.
- تست pytest: عضویت pending با start در گذشته/امروز → بعد از list/sync بشود active؛ عضویت با start آینده → pending بماند؛ پرداخت paid وضعیت future را active نکند.

### ۲) فرانت — برچسب و کپی
- `membershipStatusLabelFa` / `MEMBERSHIP_STATUS_LABEL` در `format.js`: `pending` → متنی مثل «شروع‌نشده» (نه «در انتظار»).
- اگر جایی عمداً «در انتظار پرداخت» برای membership نشان می‌دهد، جدا کن.
- `athlete-memberships.js` و لیست عضویت در `billing.js`: برچسب جدید؛ در صورت امکان یک `hint` خیلی کوتاه زیر مبلغ: «مبلغ توافقی دوره» (اختیاری ولی مفید).
- `paymentStatusLabelFa` برای پرداخت `pending` همان «در انتظار» بماند.
- vitest برای label جدید و رگرسیون پرداخت.

### ۳) docs
- `business-rules.md` بخش طرح/عضویت: یک خط — `pending` یعنی بازه هنوز شروع نشده یا فعال‌سازی پنجره؛ با رسیدن `start_date` (Asia/Tehran) سیستم به active هم‌تراز می‌شود. اشتباه گرفته نشود با `payment.pending`.
- getting-started در صورت چک‌لیست گمراه‌کننده اصلاح شود.
