## تصمیم صاحب پروژه (صریح — docs را هم هم‌خوان کن)
دیتابیس لوکال از دادهٔ seed خالی شده؛ صاحب می‌خواهد از صفر داده واقعی وارد کند.
ساخت اولین مدیر فقط با CLI/سرور (PowerShell) کافی است — UI ساخت مدیر نساز.
باید این قابلیت‌ها در UI بیاید:

### الف) کارکنان
1) پنل مدیر (`/manager/`): بخش جدید مثلاً `#staff`
   - ساخت منشی (receptionist)
   - ساخت مربی (trainer)
   - لیست کارکنان (حداقل منشی‌ها و مربی‌ها؛ مدیرها فقط نمایش فقط‌خواندنی OK)
   - ویرایش: نام، موبایل، نقش فقط بین receptionist|trainer (نه ارتقا به manager از UI)، رمز جدید اختیاری
   - «حذف» = غیرفعال‌سازی (is_active=false) — حذف ردیف از DB ممنوع
   - امکان فعال‌سازی دوباره (is_active=true)
2) پنل منشی (`/receptionist/`): بخش مثلاً `#staff` یا گسترش `#trainers`
   - فقط ساخت / ویرایش / غیرفعال / فعال مربی
   - منشی نباید بتواند منشی یا مدیر بسازد؛ API هم ۴۰۳
3) مربی و ورزشکار: هیچ دسترسی به این APIها

### ب) طرح‌های عضویت
1) هم پنل مدیر و هم پنل منشی: بخش مثلاً `#plans`
   - ساخت طرح جدید
   - ویرایش طرح موجود
   - «حذف» = غیرفعال (is_active=false)؛ حذف فیزیکی ممنوع
   - فعال‌سازی دوباره
   - لیست همهٔ طرح‌ها (فعال و غیرفعال با برچسب واضح)
2) فیلدها (طبق مدل MembershipPlan):
   - name (اجباری)
   - description (اختیاری)
   - duration_days و/یا session_count — حداقل یکی باید >0 باشد (constraint فعلی)
   - base_price_toman ≥ 0 (صفر = هدیه/آزاد OK)
   - includes_locker (چک‌باکس؛ در UI برچسب «شامل کمد»)
   - is_active
3) قانون پول: تغییر base_price_toman طرح، ردیف‌های membership/payment گذشته را عوض نکند؛ فقط تمدیدهای بعدی قیمت پایهٔ جدید را پیشنهاد دهند.
4) در billing و جاهایی که select طرح فعال است: فقط is_active=true؛ طرح غیرفعال دیده نشود (مگر لیست مدیریت طرح‌ها).

### ج) Bootstrap مدیر (حداقلی)
- یک CLI لوکال مثل `python -m app.db.bootstrap_manager --mobile ... --password ... --name ...`
- فقط وقتی صفر User با role=manager وجود دارد
- رمز در گیت نرود؛ در getting-started بخش «شروع بدون seed» کوتاه

## قوانین کسب‌وکار مرتبط (خلاصه داخل پرامپت)
- ورود یکپارچه موبایل+رمز؛ اولویت staff روی member.
- رمز کارکنان ≥۸؛ مدیر (و طبق این برش منشی فقط برای مربی‌هایی که می‌سازد/مدیریت می‌کند) بتواند رمز را عوض کند.
- حذف دائمی عضو/کارمند/طرح ممنوع — آرشیو یا is_active=false.
- چند عضویت هم‌زمان مجاز؛ اجارهٔ جدا کمد نیست.
- audit برای ساخت/ویرایش/غیرفعال کارکنان و طرح‌ها.
- سرور enforce کند؛ مخفی کردن UI امنیت نیست.

## وضعیت فعلی کد (واقعیت)
- User فقط از seed ساخته می‌شود؛ POST ساخت staff عمومی نیست؛ تغییر رمز مدیر تا حدی هست (`POST /api/v1/auth/users/{id}/password`).
- `#trainers` فقط واگذاری مربی به عضو است — ساخت حساب مربی نیست.
- membership-plans فقط GET؛ UI ساخت/ویرایش طرح نیست.
- عضو از `#members` ساخته می‌شود — دست نزن مگر لازم برای یکپارچگی ناچیز.

## پیاده‌سازی مورد انتظار

### Backend
- API تحت `/api/v1` با نقش‌ها:
  - کارکنان: مثلاً `GET/POST /api/v1/staff`، `PATCH /api/v1/staff/{id}`، `POST .../deactivate` یا PATCH با is_active
  - مدیر: receptionist + trainer
  - منشی: فقط trainer (create/update/deactivate روی trainerها)
  - طرح‌ها: `POST/PATCH /api/v1/membership-plans` (و در صورت نیاز GET شامل غیرفعال‌ها برای صفحهٔ مدیریت با query مثل `?include_inactive=1`)
  - منشی و مدیر هر دو به CRUD طرح دسترسی دارند؛ مربی ۴۰۳
- اعتبارسنجی موبایل یکتا در users؛ تداخل با members طبق قانون فعلی لاگین را در نظر بگیر (اگر موبایل در members هم باشد staff اولویت دارد — در docs/UI یک hint کوتاه).
- غیرفعال کردن کارمند: سشن‌های فعال او باطل شوند اگر الگوی فعلی پروژه اجازه می‌دهد.
- غیرفعال کردن طرح: عضویت‌های فعال فعلی همان طرح قطع نشوند مگر docs بگوید؛ فقط انتخاب برای تمدید جدید متوقف شود.

### Frontend (Ocean Dark)
- `manager.js` + HTML مدیر: لینک ناو `#staff` و `#plans` + mount
- `receptionist.js` + HTML منشی: لینک ناو برای مربی‌سازی و `#plans` + mount
- فرم‌ها فارسی RTL؛ پیام خطا از API؛ بدون کارت‌های تزئینی اضافه خارج از الگوی پنل موجود
- با الگوی `setStatus` / `apiGet` / `apiPost` / `apiPatch` موجود هم‌خوان باش
- نقش‌ها در UI فارسی: منشی / مربی / مدیر

### Docs
- business-rules و getting-started و roadmap-status را با رفتار جدید هم‌خوان کن (منشی می‌تواند مربی و طرح بسازد).
- seed را اجباری نکن برای شروع خالی؛ اگر تست‌ها به seed وابسته‌اند fixture تست را نگه دار.
