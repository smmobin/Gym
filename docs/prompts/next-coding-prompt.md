# پرامپت مرحلهٔ بعد — برای چت سازنده (Agent)

آخرین به‌روزرسانی: ۱۴۰۴-۰۷-۲۷ (مدیر محصول — پس از تأیید کمد)  
مرحله: واگذاری مربی + برنامه تمرینی ساده

کل بلاک زیر را کپی کن و در یک **چت Agent جدید** (سازنده، نه مدیر محصول) بفرست.

```text
# نقش
تو Agent سازندهٔ پروژهٔ GYM CONTROL هستی. مدیر محصول این مرحله را تأیید کرده.
docs را خودت پیدا و بخوان (از docs/README.md شروع کن).
منبع حقیقت: docs/product/business-rules.md نقش مربی + بخش «برنامه تمرینی».
مدل‌ها از قبل هست:
- backend/app/models/trainer.py (TrainerMemberAssignment با ended_at)
- backend/app/models/workout.py (WorkoutPlan: title + body متنی)
- seed: چند واگذاری مربی–شاگرد + حداقل یک برنامه نمونه
از auth و members موجود استفاده کن (مربی الان فقط شاگردهای خودش را در members می‌بیند اگر از قبل فیلتر شده؛ هم‌خوان نگه دار).
کار جدید فقط در frontend/ و backend/. پروتوتایپ HTML ریشه را تغییر نده.

# زبان با صاحب پروژه
فارسی، ساده، داخل <div dir="rtl">.
در پایان بگو کاملاً OK یا ناقص + نتیجهٔ تست.

# هدف این چت (فقط همین برش)
مدیر/منشی بتوانند عضو را به مربی وصل (و قطع) کنند. مربی فقط شاگردهای خودش را ببیند و برایشان برنامه تمرینی متنی بنویسد/ویرایش کند. مدیر به همه دسترسی دارد و می‌تواند برنامه بگذارد.

1) لیست مربیان (کاربران نقش trainer فعال)
2) واگذاری شاگرد ↔ مربی و پایان واگذاری (ended_at)
3) چند مربی هم‌زمان برای یک شاگرد مجاز است (طبق قوانین)
4) CRUD سادهٔ برنامه تمرینی (عنوان + متن) محدود به شاگردهای مجاز
5) UI React پشت لاگین: مثلاً /trainers برای desk و /trainer یا /workouts برای مربی (یا یک صفحهٔ واحد با نقش)
6) تست‌های سبز نقش و محدودهٔ دسترسی

# داخل محدوده
Backend (/api/v1):

مربیان / واگذاری:
- GET /trainers  (desk: لیست کاربران role=trainer؛ فیلدهای امن: id, full_name/mobile نمایشی)
- GET /members/{id}/trainers  واگذاری‌های فعال (+ اختیاری تاریخچه)
- POST /members/{id}/trainers  body: trainer_user_id
  - فقط manager+receptionist
  - trainer باید نقش trainer و فعال باشد
  - اگر همان جفت الان فعال است (ended_at IS NULL) → ۴۰۹
  - چند مربی مختلف برای یک عضو OK
- POST /members/{id}/trainers/{assignment_id}/end  یا POST …/unassign
  - ended_at = now؛ بعداً دوباره assign همان مربی مجاز است (ردیف جدید)

برنامه تمرینی:
- GET /members/{id}/workout-plans
  - manager: همه
  - trainer: فقط اگر واگذاری فعال به آن عضو دارد
  - receptionist: خواندن OK برای کار میز؛ نوشتن نه مگر ساده بگیری که فقط trainer+manager بنویسند (ترجیح: نوشتن = trainer برای شاگرد خودش + manager برای همه؛ receptionist فقط خواندن)
- POST /members/{id}/workout-plans  body: title, body?
- PATCH /workout-plans/{id}  title/body
- DELETE اختیاری یا soft — اگر سخت است نساز؛ در گزارش بگو

نقش‌ها (سخت‌گیر):
- trainer روی عضو غیرشاگرد → ۴۰۳
- trainer نمی‌تواند واگذاری مربی بسازد/قطع کند → ۴۰۳
- بدون لاگین → ۴۰۱
- لیست members برای trainer باید فقط شاگردهای فعال بماند (اگر الان هست تقویت/هم‌خوان کن)

Frontend:
- RTL/فارسی
- صفحهٔ desk: انتخاب عضو → دیدن مربیان فعلی → افزودن/قطع مربی
- صفحهٔ مربی: لیست شاگردها → دیدن/ایجاد/ویرایش برنامه (عنوان + متن ساده کافی است؛ ادیتور پیشرفته نساز)
- مدیر همان قابلیت‌ها را روی همه دارد
- لینک در شل/ناو موجود پروژه

Seed / Docs:
- seed را طوری نگه دار که با لاگین مربی seed (مثلاً 09120000003) حداقل یک شاگرد و یک برنامه دیده شود
- getting-started: چطور واگذاری و برنامه را امتحان کنند
- schema-todos: اگر ایندکس جزئی لازم ماند یادداشت کن
- roadmap فقط اگر مطمئنی تمام شد

# خارج از محدوده (نساز)

- تقویم پیشرفته، ویدیو، PDF، قالب ورزشی پیچیده
- کلاس، کمد، گزارش مالی، قفل پرونده، مهمان، فرم آزمایشی
- پیامک / درگاه

# قوانین کسب‌وکار مرتبط (اجرا کن)
- مربی فقط شاگردهای خودش را کامل می‌بیند؛ برای همان‌ها برنامه می‌نویسد
- یک شاگرد می‌تواند چند مربی هم‌زمان داشته باشد
- مدیر به همه دسترسی دارد و می‌تواند برنامه بگذارد
- ورزشکار در v1 لاگین ندارد → برنامه را فقط کارکنان می‌بینند
- مخفی کردن UI امنیت نیست

# کیفیت
- pytest: assign OK؛ تکراری فعال رد؛ end بعداً re-assign OK؛ trainer برنامه برای شاگرد خودش OK؛ برای غیرشاگرد ۴۰۳؛ manager همه؛ ۴۰۱
- vitest کوچک اگر منطقی است
- .env و دادهٔ واقعی در گیت نباشد
- بعد از تست سبز: commit + push به origin/main
- گزارش: endpointها، مسیرهای UI، سیاست نوشتن receptionist، چه چیز عمداً نساختی

# اگر مبهم شد
حدس نزن. business-rules نقش مربی و برنامه را اجرا کن. جزئیات فرعی را ساده بگیر و مستند کن.
```
