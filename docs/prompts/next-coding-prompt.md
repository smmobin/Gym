# پرامپت مرحلهٔ بعد — برای چت سازنده (Agent)

آخرین به‌روزرسانی: ۱۴۰۴-۰۷-۲۷ (مدیر محصول — پس از تأیید گزارش مدیر)  
مرحله: فرم آزمایشی عمومی → صف منشی + ثبت مهمان روزانه

کل بلاک زیر را کپی کن و در یک **چت Agent جدید** (سازنده، نه مدیر محصول) بفرست.

---

```text
# نقش
تو Agent سازندهٔ پروژهٔ GYM CONTROL هستی. مدیر محصول این مرحله را تأیید کرده.
docs را خودت پیدا و بخوان (از docs/README.md شروع کن).
منبع حقیقت: docs/product/business-rules.md بخش «مهمان و جلسه آزمایشی» + سایت عمومی.
مدل/seed موجود:
- TrialLead + TrialLeadStatus (new/contacted/converted/closed)
- طرح seed «مهمان یک‌روزه» (duration_days=1)
- عضو مهمان نمونه در seed
کار جدید فقط در frontend/ و backend/. پروتوتایپ HTML ریشه را تغییر نده (فرم واقعی در React عمومی باشد، نه اینکه HTML ریشه را به API وصل کنی مگر لینک ساده به مسیر React — ترجیح: صفحهٔ React عمومی).

# زبان با صاحب پروژه
فارسی، ساده، داخل <div dir="rtl">.
در پایان بگو کاملاً OK یا ناقص + نتیجهٔ تست.

# هدف این چت (فقط همین برش)
1) بازدیدکننده بدون لاگین بتواند فرم جلسهٔ آزمایشی بفرستد → ردیف در صف trial_leads
2) منشی/مدیر صف را ببینند و وضعیت را عوض کنند؛ خودکار عضو ساخته نشود
3) منشی/مدیر بتوانند «مهمان روزانه» ثبت کنند = عضو موقت + عضویت ۱روزه (+ پرداخت اختیاری/هم‌زمان ساده)
4) UI مناسب + تست سبز

# داخل محدوده
Backend (/api/v1):

فرم عمومی (بدون auth):
- POST /public/trial-leads  body: full_name, mobile, preferred_time_note?, message?
  اعتبارسنجی موبایل/نام؛ rate-limit ساده اختیاری؛ بدون ساخت Member
- CORS/cookie برای این مسیر لازم نیست (بدون نشست)

صف کارکنان:
- GET /trial-leads?status=  manager+receptionist
- PATCH /trial-leads/{id}  status (و اختیاری note) — desk only
- تبدیل به عضو: خودکار نکن؛ دکمهٔ UI می‌تواند منشی را به ساخت عضو/مهمان راهنمایی کند یا endpoint اختیاری convert که عضو موقت بسازد — اگر ساختی، صریح و تست‌شده باشد؛ پیش‌فرض: فقط تغییر وضعیت + لینک به جریان مهمان/اعضا

مهمان روزانه (desk):
- POST /guests  یا POST /members/day-guest
  body: first_name, last_name, mobile, agreed_amount_toman (>=0), payment_method?, pay_now? 
  رفتار:
  - اگر موبایل تکراری است → ۴۰۹ یا عضو موجود را مهمان روزانه تمدید/عضویت ۱روزه بده — یک سیاست ساده انتخاب و مستند کن (پیشنهاد: موبایل جدید عضو بساز؛ اگر موجود بود فقط عضویت ۱روزهٔ جدید روی همان عضو اگر منطقی است، وگرنه ۴۰۹ با پیام واضح)
  - Member با وضعیت مناسب (active)
  - Membership روی طرح «مهمان یک‌روزه» (از seed/plan با duration_days=1 و/یا نام مشخص؛ اگر پیدا نشد خطا بده نه حدس خاموش)
  - start_date=end_date=امروز تهران (یا end = start طبق duration_days طرح)
  - اگر pay_now: یک Payment paid با receipt مثل billing
  - trainer → ۴۰۳

Frontend:
- صفحهٔ عمومی بدون لاگین: مثلاً /trial  (فرم آزمایشی)
- صفحهٔ desk: /trial-leads صف درخواست‌ها + تغییر وضعیت
- جریان مهمان: /guests یا بخش در /members — فرم ثبت مهمان روزانه
- RTL/فارسی؛ تومان با جداکننده
- منشی گزارش مدیر را نبیند (دست نزن مگر لازم)

Docs:
- getting-started: آدرس /trial و /trial-leads و ثبت مهمان
- روشن کن که GitHub Pages هنوز محصول واقعی نیست
- roadmap فقط اگر مطمئنی تمام شد

# خارج از محدوده (نساز)
- لاگین ورزشکار، پیامک واقعی، درگاه آنلاین
- تنظیمات باشگاه کامل، اعلان داخل‌برنامه (برش بعد)
- وصل کردن HTML ریشه به‌عنوان backend واقعی
- فروشگاه / چند شعبه
- تغییر رفتار billing/گزارش مگر لازم برای پرداخت مهمان

# قوانین کسب‌وکار مرتبط (اجرا کن)
- مهمان روزانه = عضو موقت با اشتراک ۱روزه (موبایل یکتا)
- منشی می‌تواند مهمان ثبت کند و پول بگیرد
- فرم سایت → درخواست در صف منشی؛ خودکار عضو ساخته نمی‌شود
- مخفی کردن UI امنیت نیست

# کیفیت

- vitest کوچک اگر منطقی است
- .env و دادهٔ واقعی در گیت نباشد
- بعد از تست سبز: commit + push به origin/main
- گزارش: endpointها، مسیرهای UI عمومی vs desk، سیاست موبایل تکراری، آیا convert خودکار آمد یا نه، چه چیز عمداً نساختی

# اگر مبهم شد
حدس نزن. business-rules مهمان/آزمایشی را اجرا کن. جزئیات فرعی را ساده بگیر و مستند کن.
```
