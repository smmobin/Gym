مرحله: مدل‌های دیتابیس + اولین migration + seed فیک

کل بلاک زیر را کپی کن و در یک **چت Agent جدید** (سازنده، نه مدیر محصول) بفرست.

```text
# نقش
تو Agent سازندهٔ پروژهٔ GYM CONTROL هستی. مدیر محصول این مرحله را تأیید کرده. docs و قوانین را خودت پیدا و بخوان (از docs/README.md شروع کن). منبع حقیقت رفتار محصول: docs/product/business-rules.md — اگر با پروتوتایپ HTML یا مدل نمونهٔ قدیمی تعارض داشت، business-rules مقدم است.

# زبان با صاحب پروژه
فارسی، ساده، داخل <div dir="rtl">. اصطلاح فنی را یک جمله توضیح بده. در پایان بگو کاملاً OK یا ناقص.

# هدف این چت (فقط همین برش)
1) مدل‌های SQLAlchemy مطابق قوانین کسب‌وکار برای نسخهٔ اول
2) اولین migration Alembic که روی Postgres محلی gym_control اعمال شود
3) اسکریپت seed با دادهٔ ساختگی سازگار (حداقل حدود ۸ عضو + چند طرح مدت‌دار و جلسه‌ای + عضویت‌های فعال/نزدیک به انقضا/منقضی + پرداخت کامل و بدهی + حضور ورود/خروج + تنظیمات باشگاه + حداقل ۱ کلاس با ظرفیت + ۲ کمد + ۱–۲ مربی و شاگرد)
4) تست خودکار سبز برای: health قبلی نشکند؛ migration قابل اعمال باشد؛ محدودیت‌های مهم (موبایل یکتا، مبلغ توافقی ≥ ۰، seed اعداد داشبورد-منطق بدهی را نقض نکند)

# داخل محدوده
- جدول‌ها / مدل‌ها تقریباً برای کل نسخهٔ اول (تا بعداً migration تکه تکه و ناسازگار نشود)، از جمله:
  users (کارکنان: manager / receptionist / trainer، password_hash برای بعد، بدون endpoint لاگین)
  members (موبایل یکتا اجباری، شناسهٔ نمایشی M-1001…، بدون حذف سخت — soft archive)
  membership_plans (مدت روز و/یا تعداد جلسه، قیمت پایه، فعال/غیرفعال، آیا شامل کمد)
  memberships (جدا از عضو؛ مبلغ توافق‌شده؛ شروع/پایان؛ وضعیت؛ freeze در حد فیلدهای لازم)
  payments (روش cash/pos/transfer/online؛ وضعیت paid/pending/refunded؛ ویرایش مستقیم نباشد — مدل اجازهٔ «اصلاح با ویرایش مبلغ» ندهد)
  attendances (check_in / check_out؛ نوع gym/class/pt)
  gym_settings (نام، تماس، آدرس، ساعت پایان روز پیش‌فرض ۲۳:۰۰، روز هشدار انقضا ۷، سقف freeze)
  audit_logs (جدول آماده؛ نوشتن رویداد کامل می‌تواند حداقل باشد)
  group classes + bookings (ظرفیت؛ بدون overbook در منطق اگر راحت است یک helper/چک ساده)
  lockers + assignment
  trainer_member assignments (چند مربی برای یک شاگرد)
  workout_plans حداقل اسکلت
  trial_leads (صف فرم آزمایشی)
  expenses (دسته + مبلغ + تاریخ برای مدیر)
- دستور اجرای seed در docs/guides/getting-started.md
- به‌روز کردن docs/product/roadmap-status.md فقط در حد «این مرحله انجام شد / نشد» اگر ازت خواسته شده؛ اگر مطمئن نیستی مدیر محصول بعداً به‌روز می‌کند — ولی getting-started و توضیح seed را حتماً بنویس
- کار فقط در frontend/ در این مرحله لازم نیست مگر تایپ مشترک خیلی کوچک؛ تمرکز backend است

# خارج از محدوده (نساز)
- لاگین / نشست / JWT / صفحهٔ ورود
- پنل React اعضا/منشی/مدیر/مربی (صفحهٔ اسکلت خانه بماند)
- پیامک واقعی، درگاه پرداخت واقعی
- تغییر یا حذف پروتوتایپ HTML ریشه
- Docker کامل، جدا کردن ریپو، Dependabot در این برش مگر برای تست لازم شود
- دادهٔ واقعی انسان‌ها در seed

# قوانین کسب‌وکار که مدل باید بتواند پیاده کند (حالا یا با فیلد آماده)
- درآمد ≠ بدهی؛ بدهی از مبلغ توافقی عضویت منهای پرداخت paid
- پرداخت ناقص مجاز
- تمدید از پایان اشتراک فعلی (روز نسوزد) — در مدل با ردیف membership جدید قابل بیان باشد
- اشتراک منقضی → بعداً ورود ممنوع؛ بدهی با اشتراک معتبر → ورود مجاز
- صفر تومان توافقی مجاز، منفی نه
- حذف عضو = archive نه DELETE فیزیکی
- روش online در enum باشد ولی هیچ اتصال درگاهی نساز

# کیفیت
- Postgres؛ SQLAlchemy 2؛ Alembic از DATABASE_URL موجود
- هیچ رمز در گیت؛ .env را commit نکن
- تست pytest سبز، بعد commit و push به origin/main طبق قانون پروژه
- گزارش: نتیجهٔ تست، چه جدول‌هایی آمد، چطور seed اجرا شود، چه چیزی عمداً ساخته نشد

# اگر مبهم شد
حدس نزن. همان قوانین business-rules را اجرا کن. اگر یک جزئی مدل بدون تصمیم ماند، در docs یک TODO کوتاه بنویس و در گزارش بگو — جدول را بلاک نکن.
```
