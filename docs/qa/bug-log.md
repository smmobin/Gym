## باگ‌ها

### BUG-001 — مسیر واگذاری کمد برای عضو بدون طرح شامل‌کمد گیج‌کننده است
- **شدت:** Major
- **نقش / صفحه:** مدیر و منشی → `/manager/#lockers` و `/receptionist/#lockers` (+ ایجاد عضو / تمدید در billing)
- **محیط:** لوکال :8000 (+ :5173 وقتی روشن) | seed | API تأیید شد
- **مراحل تکرار:**
  1. لاگین مدیر `09120000001` / `ChangeMe123`
  2. `#lockers` → کمد آزاد (مثلاً L-03) را انتخاب کن
  3. جستجوی عضو → «علی رضایی» (اشتراک فعال دارد) → واگذاری
  4. مشاهدهٔ پیام: «این عضو عضویت فعال با طرح شامل‌کمد ندارد»
  5. مقایسه: برای «سارا محمدی» (طرح «سه‌ماهه + کمد») واگذاری ممکن است
- **انتظار (از دید میز):** عضو با اشتراک فعال بتواند کمد بگیرد، یا حداقل UI روشن بگوید کدام اعضا/طرح‌ها واجد شرایط‌اند و از ثبت عضو/تمدید بتوان به طرح شامل‌کمد رسید
- **واقعیت (قبل از فیکس):** رفتار سرور مطابق `business-rules.md` §۸؛ UI پیام کوتاه بدون قدم بعد؛ بدون لیست واجدین؛ بدون برچسب «شامل کمد» در billing
- **فیکس:** پیام واضح + لینک `#billing`؛ لیست `GET /lockers/eligible-members`؛ برچسب واجد/بدون کمد روی عضویت‌های عضو انتخاب‌شده؛ برچسب «شامل کمد» در select طرح billing؛ یادآوری در فرم عضو جدید. قانون اجارهٔ جدا عوض نشد.
- **وضعیت:** بسته‌شده

### BUG-003 — بعد از ساخت کمد، لیست تا refresh صفحه به‌روز نمی‌شود
- **شدت:** Minor
- **نقش / صفحه:** مدیر/منشی → بخش کمدها → فرم «ساخت کمد»
- **واقعیت کد:** بعد از `apiPost` تابع `load()` صدا زده می‌شد، ولی `Promise.all` با `membership-plans` اگر یکی fail می‌شد کل رندر جدول را هم می‌برد.
- **فیکس:** بارگذاری جدول کمد از بارگذاری طرح‌ها جدا شد؛ در شکست بازخوانی، ردیف ساخته‌شده به‌صورت optimistic در جدول می‌آید؛ vitest مسیر create→لیست اضافه شد.
- **وضعیت:** بسته‌شده

### BUG-004 — چند عضویت شامل‌کمد فعال؛ UI بدون انتخاب، اولی را می‌فرستد
- **شدت:** Suggestion
- **نقش / صفحه:** مدیر/منشی → `#lockers` واگذاری
- **محیط:** لوکال :8000 | DB زنده (چند طرح با includes_locker=true) | 2026-10-27
- **مراحل تکرار:**
  1. عضوی با بیش از یک عضویت فعال شامل‌کمد (مثلاً علی وقتی چند طرح locker دارند)
  2. `POST /lockers/{id}/assign` بدون `membership_id` → ۴۰۰ «چند عضویت… صریح بفرستید»
  3. در UI دکمه واگذاری → همیشه `eligible[0].id` ارسال می‌شود؛ انتخابگر عضویت نیست (برچسب واجد/بدون کمد فقط نمایشی است)
- **انتظار:** اگر بیش از یکی واجد است، میز بتواند عضویت مرجع را انتخاب کند (یا حداقل بداند کدام انتخاب شده)
- **واقعیت:** منطق سرور درست است؛ UX انتخاب ندارد و اولین واجد را بی‌صدا می‌فرستد
- **شواهد:** API ۴۰۰ بدون membership_id؛ `lockers.js` خط `membership_id: eligible[0].id`
- **احتمال دامنه:** frontend
- **وضعیت:** باز

### BUG-005 — ویزارد ورود لود نمی‌شود؛ بعد از موبایل همان صفحه برمی‌گردد
- **شدت:** Critical
- **نقش / صفحه:** همه → `/login/`
- **محیط:** لوکال frontend (مثلاً `:5174`) + backend `:8000` | Chrome automation | 2026-10-27
- **مراحل تکرار:**
  1. باز کردن `/login/`
  2. موبایل مدیر `09120000001` → «ادامه»
  3. همان فرم موبایل می‌ماند؛ URL می‌شود `/login/?mobile=09120000001` (submit بومی GET)
- **انتظار:** برای مدیر/منشی → مرحله رمز؛ برای مربی/ورزشکار → مرحله OTP (با امکان سوییچ به رمز)
- **واقعیت:** ماژول `frontend/assets/js/panels/login.js` با خطای `Invalid left-hand side in assignment` لود نمی‌شود (انتساب روی cast جی‌اس‌داک: `/** @type {HTMLElement} */ (el).hidden = …`). بدون JS، `preventDefault` نیست → رفرش همان صفحه. API `POST /auth/lookup` سالم است و هویت‌ها درست برمی‌گردند
- **شواهد:** Console: `reimport_fail: Invalid left-hand side in assignment`؛ lookup مدیر → `auth_methods: ["password"]`؛ مربی/ورزشکار → `["otp","password"]`؛ Vite scan روی همان خط PARSE_ERROR
- **احتمال دامنه:** frontend (یک خط در `showStep`)
- **فیکس:** `showStep` به `login-ui.js` منتقل شد؛ انتساب `hidden` روی متغیر `HTMLElement` واقعی (بدون cast به‌عنوان LHS). vitest: `showStep` + گارد منبع برای الگوی cast.
- **وضعیت:** بسته‌شده

### BUG-006 — انتخاب روز در date-picker نوع datetime-local (کلاس‌ها) ثبت نمی‌شود
- **شدت:** Major
- **نقش / صفحه:** منشی/مدیر → `/receptionist/#classes` یا `/manager/#classes` → ساخت/ویرایش → شروع/پایان
- **محیط:** لوکال `:5174` + `:8000` | پنل منشی | 2026-10-27
- **مراحل تکرار:**
  1. لاگین منشی → `#classes` → فرم ساخت/ویرایش کلاس
  2. روی فیلد «شروع» یا «پایان» کلیک کن (تقویم جلالی باز می‌شود — این بخش OK است)
  3. روی یک روز دیگر تقویم کلیک کن (مثلاً ۲۰)
- **انتظار:** همان روز انتخاب شود؛ برای datetime پاپ‌آپ باز بماند تا ساعت تنظیم و «تأیید» زده شود؛ مقدار مخفی `datetime-local` به‌روز شود
- **واقعیت:** با کلیک روی روز، `renderGrid()` دکمهٔ روز را از DOM حذف می‌کند؛ listener سراسری `document.click` گمان می‌کند کلیک بیرون بوده (`root.contains(detachedNode) === false`) → برای withTime مقدار را از input خالی برمی‌گرداند و پاپ‌آپ را می‌بندد. برچسب ممکن است «امروز» بماند؛ `input.value` خالی بماند تا وقتی فقط ساعت را عوض کنند و تأیید بزنند (بدون کلیک روز)
- **شواهد:** بعد از `day.click()` → `dayStillInDocument: false`، `open: false`، `value: ""`؛ پاپ‌آپ از نظر باز شدن اولیه و نمایش جلالی سالم است
- **احتمال دامنه:** frontend — `frontend/public/js/date-picker.js` (+ کپی `assets/js/date-picker.js` اگر sync لازم است)
- **فیکس:** `stopPropagation` روی کلیک روز قبل از `renderGrid`؛ outside-click اگر `target` از DOM جدا شده باشد نادیده گرفته می‌شود. کپی `assets/js` و `public/js` sync. vitest: datetime روز ۲۰ → باز می‌ماند؛ تأیید → value پر.
- **وضعیت:** بسته‌شده

### BUG-007 — ذخیرهٔ مکرر کلاس → ردیف‌های تکراری یکسان
- **شدت:** Major
- **نقش / صفحه:** منشی → `#classes` → ساخت/ویرایش → ذخیره
- **محیط:** لوکال | seed + دادهٔ دستی | 2026-10-27
- **مراحل تکرار:**
  1. فرم کلاس را پر کن (مثلاً «کلاس ۵ نفره مردان» + زمان)
  2. چند بار «ذخیره» بزن (بدون زدن «جدید» و بدون ویرایش از لیست)
- **انتظار:** بار اول ایجاد؛ بارهای بعد یا همان رکورد آپدیت شود، یا دکمه تا اتمام درخواست غیرفعال باشد، یا سرور از تکراری عنوان+شروع+جنسیت جلوگیری کند
- **واقعیت:** بعد از create موفق، `form.reset()` فیلد مخفی `id` را خالی می‌کند → هر ذخیرهٔ بعدی دوباره `POST` جدید است. قفل دابل‌کلیک نیست. سرور uniqueness روی (title, starts_at) ندارد
- **شواهد:** ۱۵ کلاس دستی تکراری (۹+۳+۳) با `booked_count=0`؛ QA ۱۲تای اضافه را با `PATCH is_active=false` غیرفعال کرد و از هر گروه یکی نگه داشت (باقی: 2701 مردان ۱۶:۰۴، 2704 بانوان ۱۶:۰۴، 2713 بانوان ۱۲:۰۴)
- **احتمال دامنه:** frontend (+ اختیاری backend uniqueness / دکمه حذف یا غیرفعال در UI)
- **فیکس:** بعد از create موفق، `id` برگشتی در فرم می‌ماند (ذخیرهٔ بعد = PATCH)؛ قفل `busy` + disable دکمهٔ ذخیره هنگام درخواست؛ سرور برای کلاس فعال هم‌عنوان+شروع+جنسیت → ۴۰۹ فارسی؛ دکمهٔ «غیرفعال‌سازی» برای کلاس بدون رزرو (`PATCH is_active=false`). vitest + pytest.
- **وضعیت:** بسته‌شده

### BUG-008 — بعد از ذخیره، لیست کلاس فوری همان آیتم را جلو چشم نمی‌آورد
- **شدت:** Major
- **نقش / صفحه:** منشی/مدیر → `#classes` جدول بالا
- **محیط:** لوکال | صفحه‌بندی ۵تایی | 2026-10-27
- **مراحل تکرار:**
  1. روی صفحهٔ آخر لیست باش یا کلاس جدید با تاریخ آینده بساز
  2. ذخیره کن
  3. لیست بالا همان لحظه کلاس جدید را نشان نمی‌دهد مگر قبلی/بعدی
- **انتظار:** بعد از mutation، لیست فوری به‌روز شود و ترجیحاً به صفحه‌ای که رکورد جدید/ویرایش‌شده هست برود (یا اول لیست بر اساس تازه‌ترین)
- **واقعیت:** `autoRefresh.refresh()` صدا زده می‌شود ولی ترتیب API `starts_at asc` است و pager بعد از reset روی صفحهٔ ۱ می‌ماند (کلاس‌های seed قدیمی)؛ کلاس جدید روی صفحات بعدی است. `emitLive(LIVE.CLASSES)` بعد از ذخیره نیست. الگوی مشابه برای «همهٔ لیست‌های سایت» نیاز به قرارداد واحد دارد
- **شواهد:** اسکرین صاحب — صفحه ۴ از ۴ با چند ردیف یکسان؛ total بعد از پاکسازی QA از ۱۹ به ۷ رسید
- **احتمال دامنه:** frontend (classes + pagination/live pattern)
- **وضعیت:** باز
