# وضعیت نقشهٔ راه — GYM CONTROL

**آخرین به‌روزرسانی:** ۱۴۰۴-۰۷-۲۳ (2026-10-15) — پس از برش مدل + migration + seed  
**نقش:** سند زندهٔ مدیر محصول — بعد از هر مرحلهٔ انجام‌شده باید عوض شود.

## الان کجاییم؟

اسکلت فرانت/بک، قوانین کسب‌وکار، و **مدل‌های SQLAlchemy نسخهٔ اول + migration Alembic + seed ساختگی** روی Postgres محلی `gym_control` آماده‌اند.  
هنوز لاگین کارکنان و پنل‌های React عملیاتی ساخته نشده‌اند.

## انجام شده

- پروتوتایپ UI و تم Ocean Dark (GitHub Pages)
- اسکلت `frontend/` و `backend/` + تست health
- قوانین پروژه، امنیت، ADR پشته
- قوانین کسب‌وکار محصول (نقش، پول، حضور، کلاس، …)
- مدل‌ها / جدول‌های v1 + اولین migration (`2ac5732e2cdb_v1_initial_schema`)
- اسکریپت seed (`python -m app.db.seed`) + تست قیود و منطق بدهی

## الان نکن

- لاگین واقعی و پنل React کامل (الان نوبت auth/برش عضو است)
- پیامک واقعی / درگاه آنلاین واقعی
- دادهٔ واقعی عضو در گیت یا seed
- جدا کردن ریپو یا Docker کامل مگر مرحلهٔ جدا و تأییدشده
- دست زدن به HTML ریشه به‌عنوان محصول واقعی

## مرحلهٔ بعد (همین حالا)

**یک جمله:** ورود کارکنان واقعی (موبایل + رمز، نقش روی سرور) تا بعد بتوان برش «لیست/ثبت عضو» را امن ساخت.

| چیست به زبان ساده | یعنی چه |
|-------------------|--------|
| auth | تشخیص کی وارد شده (منشی/مدیر/مربی) |
| نقش سمت سرور | UI قایم‌کردن کافی نیست؛ API باید دسترسی را چک کند |

## بعد از آن (صف، نه همزمان)

1. برش «لیست/ثبت عضو» API + حداقل UI
2. حضور ورود/خروج
3. تمدید + پرداخت + audit
4. کلاس / کمد / مربی به‌ترتیب ارزش روزانه
5. پنل ورزشکار وقتی کارکنان پایدار شد
6. HTTPS و بکاپ قبل از دادهٔ واقعی باشگاه
